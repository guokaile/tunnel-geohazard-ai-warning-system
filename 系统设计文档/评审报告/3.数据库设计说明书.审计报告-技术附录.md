## P0-1 `data_sample_minute` 唯一键违反 MySQL 分区约束，**建表必然失败**

### 问题
文档 3.6.4（L422）定义：

```
主键：PRIMARY KEY(id, ts_minute)；唯一键：uk_point_minute(point_id, ts_minute)；按月分区。
```

分区键是 `ts_minute`（L415 标注"**分区键**"），而 `uk_point_minute(point_id, ts_minute)` 的列是 `(point_id, ts_minute)`——**不含 `ts_minute`**，直接违反 MySQL 分区表唯一键约束。

### 原理/证据
MySQL 官方手册 [26.6.1 Partitioning Keys, Primary Keys, and Unique Keys](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/partitioning-limitations-partitioning-keys-unique-keys.html) 明确规定：

> "All columns used in the partitioning expression for a partitioned table must be part of every unique key that the table may have."
> "every unique key on the table must use every column in the table's partitioning expression. (This also includes the table's primary key…)"
> `ERROR 1503 (HY000): A PRIMARY KEY must include all columns in the table's partitioning function`
> （手册另一处示例输出 `ERROR 1491 (HY000)`，同一约束、同一条消息文本，MySQL 各版本报码不同）

逐表核对结论：

| 表 | 分区键 | 主键 | 唯一键 | 是否满足约束 |
|---|---|---|---|---|
| `data_sample` | `ts` | `(id, ts)` | 无 | ✅ 满足（`ts` 在主键中） |
| `data_sample_minute` | `ts_minute` | `(id, ts_minute)` | `uk_point_minute(point_id, ts_minute)` | ❌ **违反**，`ts_minute` 不在该唯一键中 |

### 后果
1. `schema/01_tables.sql` 中聚合表 DDL 执行即中断，**整个初始化脚本失败**，安装向导第 6 步（架构文档 L395）无法完成 → NFR-D2"≤30min 安装"不成立。
2. 若脚本按"逐语句容错"方式执行（安装包常见写法），则**聚合表根本不存在**；分钟聚合任务当天 01:00 首次运行抛 `Table doesn't exist`，此后所有依赖聚合表的功能静默失效。
3. 反直觉的次生风险：分钟聚合正是**速率/突变/趋势判定（统计通道）**的唯一数据源（架构文档 L214、L220）。该表不存在 → FR-301 速率/突变规则、FR-601 趋势预测、FR-602 突变检测、FR-203 曲线统计**全部不可用**，即系统退化为"纯阈值报警器"。

### 修复建议
去掉代理主键 `id`，直接用业务主键（同时解决分区约束与 P1-1 聚簇键问题）：

```sql
CREATE TABLE `data_sample_minute` (
  `point_id`      bigint unsigned NOT NULL COMMENT '点位id',
  `ts_minute`     datetime(3)     NOT NULL COMMENT '分钟时间（分区键，取整到分钟）',
  `avg_value`     decimal(16,4)   NOT NULL COMMENT '均值',
  `min_value`     decimal(16,4)   NOT NULL COMMENT '最小值',
  `max_value`     decimal(16,4)   NOT NULL COMMENT '最大值',
  `first_value`   decimal(16,4)   DEFAULT NULL COMMENT '分钟首值（速率计算用）',
  `last_value`    decimal(16,4)   DEFAULT NULL COMMENT '分钟末值（速率计算用）',
  `sample_count`  int unsigned    NOT NULL COMMENT '样本数（>0）',
  `expect_count`  int unsigned    NOT NULL COMMENT '应到样本数（完整率计算用）',
  `quality_ratio` decimal(5,4)    NOT NULL DEFAULT 0 COMMENT '异常样本占比',
  `is_manual_flag` tinyint unsigned NOT NULL DEFAULT 0 COMMENT '是否含人工标记样本',
  PRIMARY KEY (`point_id`, `ts_minute`),           -- 分区列 ts_minute 已包含
  KEY `idx_ts_point` (`ts_minute`, `point_id`)      -- 支撑"某时段全线/全断面"查询
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  COMMENT='分钟聚合数据表（按月分区，仅存非空分钟）'
PARTITION BY RANGE COLUMNS(`ts_minute`) (
  PARTITION p202601 VALUES LESS THAN ('2026-02-01 00:00:00.000'),
  PARTITION p202602 VALUES LESS THAN ('2026-03-01 00:00:00.000'),
  -- ……
  PARTITION pmax    VALUES LESS THAN (MAXVALUE)      -- 兜底，见 P0-5
);
```

> 若坚持保留 `id`（雪花），唯一键必须写成 `uk_point_minute(point_id, ts_minute)` 且**主键改为 `(point_id, ts_minute)`**——即 `id` 降级为普通列并去掉主键地位，否则无论如何都建不起来。

## P0-2 字典值溢出列类型：`item_type` 取值 101~602 无法存入 `tinyint unsigned`

### 问题
- L357 / L378：`item_type tinyint unsigned NOT NULL COMMENT '测项（字典…）'`
- L674 字典表：`item_type | 101=围岩位移，102=锚杆轴力，103=钢架应力，201=涌水量，202=水压，203=地下水位，301=CH4浓度，302=CO浓度，303=H2S浓度，304=风速，401=泥水流量，402=孔隙水压，501=沉降量，502=下沉速率，601=净空收敛，602=周边位移`

`tinyint unsigned` 的取值范围是 **0~255**。字典中 301、302、303、304、401、402、501、502、601、602 共 **10 个值超出范围**。

### 原理/证据
MySQL 严格模式（8.0 默认 `sql_mode` 含 `STRICT_TRANS_TABLES`）下插入 301 到 `tinyint unsigned` 报错：

```
mysql> CREATE TABLE t(item_type tinyint unsigned NOT NULL);
mysql> INSERT INTO t VALUES (301);
ERROR 1264 (22003): Out of range value for column 'item_type' at row 1
```

### 后果
1. 受影响的是**瓦斯及有害气体（CH₄/CO/H₂S/风速）与涌水、沉降、收敛位移**全部测项——即需求 1.2.2 六大监测对象中的 **5 类无法建立点位**。
2. `mon_point` 写入失败 → 该测项点位无法配置 → 对应传感器数据无点位可挂 → 直接导致项目验收失败。
3. 这是一处**"文档内部自洽性"错误**（表定义与字典定义互相矛盾），说明字典域与表结构域未经交叉评审。

### 修复建议
```sql
-- 方案A（推荐）：放宽为 smallint unsigned（0~65535），语义不变、零迁移成本
`item_type` smallint unsigned NOT NULL COMMENT '测项字典（见sys_dict_item.item_value，101~602）',
```
同步修改 `mon_rule.item_type`（L378）、`warn_event.item_type`（L465）——两处同为 `tinyint unsigned`，同样溢出。

```sql
-- 方案B：压缩字典编码至 0~255（101→1、201→2……），保持 tinyint
--   代价：所有 3.7.1 引用、默认规则集脚本 data/03_default_rule.sql、前端枚举需同步改
```

**并新增自查脚本**（建议纳入 `schema/99_verify.sql`）：

```sql
-- 校验所有字典值都能装进其引用列的类型
SELECT dt.dict_code, di.item_value
FROM sys_dict_item di JOIN sys_dict_type dt ON dt.id = di.dict_type_id
WHERE dt.dict_code IN ('item_type','hazard_type','warn_level','warn_status')
  AND CAST(di.item_value AS UNSIGNED) > 255;
```

## P0-3 聚合表无 DDL，且文档三处互相矛盾

### 问题
| 位置 | 原文 | 矛盾点 |
|---|---|---|
| L765（附录 A 标题） | "关键表完整 DDL 示例（**其余 32 表**阶段7按 3.6 规格生成）" | 附录 A 给了 2 张表（data_sample、warn_event），35−2=**33**，不是 32 |
| L742（3.11 脚本清单） | "`schema/02_partition.sql` # 分区初始化（**当年+次年 24 个分区**）" | 未区分原始表（1 年）与聚合表（3 年，需 ≥36 个分区） |
| L118（3.5.1） | "初始化脚本预建当年+次年共 24 个分区" | 同上，未区分两表保留期差异 |
| L422 | 聚合表主键/唯一键/分区只给了**一句话描述** | 无 DDL、无字符集、无 COMMENT、无分区边界 |

### 后果
1. **聚合表实际不可创建**：3.6.4 的字段表只列了 8 个字段（L413-L420），没有 `create_time`（3.2 要求），没有字符集/排序规则声明，没有表 COMMENT（3.2"所有表与列必须有 COMMENT"），没有分区边界值。阶段7 编码人员**只能自行发明**，必然与 P0-1 的唯一键约束撞车。
2. **关键外键链路断裂**：`warn_notify_log`（L490）定义 `channel_type tinyint unsigned`，而实际通道实体表是 `sys_notify_channel`，其主键是 `id`、业务键是 `channel_code varchar(32)`——**两张表之间没有任何可关联的字段**。同样 `warn_event`、`warn_dispose_task`、`patrol_*` 等表也一律没有 `create_by`/`update_by`（3.2 未要求，`sys_user` 自带，说明该字段是"选择性出现"）。结果是：<br>① "通知发送失败率按通道统计"（FR-703 通道健康检测）无法用 SQL 直接完成，只能靠 `channel_type` 枚举硬匹配；② `sys_notify_channel.channel_code`（业务可配、可改名）与 `channel_type`（1/2/3 枚举）**双轨并存**，配置改 `channel_code` 时历史通知记录无法跟随；③ 一旦未来新增通道（如二期电话语音，字典已预留 `4=电话语音`），`channel_type` 又成了硬编码枚举。
3. 更严重的是"**省略**"本身产生了歧义：3.6 开头的规格声明（L134）说"必备字段 `id/create_time/update_time/is_deleted` 统一省略不逐表重复（特例注明）"。读者会认为聚合表**也有** `is_deleted`——但 3.2（L33）又说 data_sample/data_sample_minute 是特例、不设自增与逻辑删除。**同一张表在两处得到相反结论**，且聚合表未被列入附录 A 的"已给 DDL"清单，等于无人负责。
4. 直接影响交付：架构文档 L388 明确安装包须含"建表 SQL 脚本"，NFR-D2 要求"初始化脚本幂等可重复执行"——一个必然失败的 DDL 使这两条都无法验收。

### 修复建议
1. 附录 A 补齐 `data_sample_minute` 完整 DDL（用 §P0-1 的改写版）。
2. 全库统一"通道关联口径"，消除 `channel_type` 硬编码：

```sql
-- warn_notify_log：改为以 channel_id 关联实体表，保留 channel_code 快照便于历史追溯
ALTER TABLE `warn_notify_log`
  ADD COLUMN `channel_id`   bigint unsigned NOT NULL COMMENT '通知通道id（sys_notify_channel.id）' AFTER `event_id`,
  ADD COLUMN `channel_code` varchar(32) NOT NULL COMMENT '通道编码快照（配置改名后仍可追溯）' AFTER `channel_id`,
  DROP COLUMN `channel_type`;
-- 同理 warn_remind_log / sys_notify_template 统一用 channel_code 关联，不再用 tinyint 枚举
```
3. 3.6 开头的"规格说明"改为**显式例外清单**而非"统一省略"：

```markdown
> 规格说明：下列为必备字段默认定义，除「例外清单」外所有表均包含：
> id bigint unsigned NOT NULL AUTO_INCREMENT、create_time datetime NOT NULL DEFAULT CURRENT_TIMESTAMP、
> update_time datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP、
> is_deleted tinyint unsigned NOT NULL DEFAULT 0
>
> 例外清单：
> - data_sample / data_sample_minute：无 id/自增、无逻辑删除、无 update_time（分区表特例）
> - data_point_latest：无 create_time（单行 upsert 表）
> - sys_oper_log / sys_login_log / warn_event：无 is_deleted（仅追加/永久保留）
> - 各关联表（sys_user_role 等）：仅 id + create_time
```

3. `02_partition.sql` 拆为两段，分别按各表保留期预建：

```sql

-- data_sample_minute：保留 3 年 → 预建 39 个分区（当月 + 未来 38 个月）

```

## P0-4 秒级 `datetime` + 无去重键 = 补传时"丢数"与"重复"二选一

### 问题
1. `data_sample.ts` / `data_sample_minute.ts_minute` 均为 `datetime`（秒级，L401/L415）；
2. 采集周期最小 30s（L362 `collect_freq_sec` 30~1800；需求 L79 "30s~5min"）；
3. `data_sample` **没有任何唯一键**（L407：主键 `(id, ts)`，`id` 是应用生成的雪花）；
4. 手工录入（`source=3`）与文件导入（`source=4`）在同一秒内可产生多条。

### 原理/证据
**场景 A（重复）：** FR-101（L156）要求"断点续传、重连补传"，NFR-R2（L268）要求"网络恢复后自动补传"。补传时网关按**补传时刻**或原采样时刻打时间戳——无论哪种，同一逻辑样本进入系统两次的概率极高（重连握手未收到 ACK、网关重发）。由于 `id` 由应用侧雪花生成，两次补传生成**两个不同 id**：

```sql
-- 同一秒同一测项的重复样本，数据库层完全无法识别
INSERT INTO data_sample(id, point_id, ts, value, source, receive_time) VALUES
 (1001, 88, '2026-10-05 02:00:00', 0.512, 1, NOW()),
 (1002, 88, '2026-10-05 02:00:00', 0.512, 1, NOW());
-- 2 rows affected —— 两条都进去了，idx_point_ts 也无法阻止
```

后果：`data_sample_minute.sample_count` 被系统性放大 → `avg_value` 失真、`quality_ratio` 失真 → FR-801"数据完整率"报表口径不可信。

**场景 B（丢数）：** 若按审阅意见把主键改成 `(point_id, ts)`（推荐），改为 `INSERT IGNORE` / `ON DUPLICATE KEY UPDATE` 去重，则**真正的两条同秒样本会被静默丢弃**，直接违反 FR-101 验收要点"数据**零丢失**"（L155）与 NFR-R2（L268）。而且丢的是哪个值无法知晓：

```sql
INSERT IGNORE INTO data_sample(point_id, ts, value, source, receive_time)
VALUES (88,'2026-10-05 02:00:00', 0.512,1,NOW()),
       (88,'2026-10-05 02:00:00', 0.531,1,NOW());
-- 1 row affected —— 第二条被静默吞掉，无告警、无留痕
```

**速率计算的量化误差：** 阈值/速率规则要计算 `(v2−v1)/(t2−t1)`。`datetime` 秒级截断使 Δt 的量化误差最多 ±1s：对 30s 窗口是 **3.3%**；而两路时钟漂移 30s 时，Δt 计算直接错 **100%**（例：真实间隔 30s，因两端时钟不同步算出 60s 或 0s）。

**"缺失"质量位无法表达：** `quality=3 缺失`（L403/L677）需要一条 value 为空的行。但 `value decimal(16,4) NOT NULL`，只能写 `0` 或 `-9999` 之类的魔法值。而真实测量值本来就可能为 0（如涌水量为 0、CH₄ 本底为 0），**缺失与真实零值不可区分**——这正是"异常数据不静默丢弃"术语（需求 L30）要防止的。

### 后果
- 去重（FR-102 明文要求"重复数据剔除"，L156）与零丢失（FR-101）在现设计下**不可同时满足**；
- 速率/突变判定的输入本身带 ±3.3%~100% 误差，**误报与漏报的根因在数据层**，算法层无法补救；
- 瓦斯浓度上升速率（需求 L79 明确列为主要预警依据）的判定精度不可辩护。

### 修复建议
```sql
-- 1) 时间精度提升到毫秒（保留 3 位小数，列定义与默认值必须同精度）
`ts`           datetime(3) NOT NULL COMMENT '采样时间（分区键，毫秒精度）',
`receive_time` datetime(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '入库时间',

-- 2) 幂等键：显式区分"业务去重键"与"重传序号"，二者都要落库
`sample_seq`   bigint unsigned NOT NULL DEFAULT 0 COMMENT '网关侧采样序号（补传/重连去重键，0=非网关来源）',
`dedup_key`    char(32) GENERATED ALWAYS AS
               (MD5(CONCAT_WS('|', point_id, DATE_FORMAT(ts,'%Y%m%d%H%i%s%f'), value))) STORED
               COMMENT '内容指纹（脱敏采样去重）',

PRIMARY KEY (`point_id`, `ts`),
UNIQUE KEY `uk_dedup` (`dedup_key`),   -- 分区列 ts 不在其中 → 见下方说明
```

> ⚠️ **注意**：`uk_dedup(dedup_key)` 同样违反分区约束（P0-1），因此**不能**建为唯一键。正确做法是把去重放在**应用层 + 落库留痕**：
> ```sql
> -- 重传清单表（记录"收到过但被判定为重复"的样本，保证 FR-102 可审计）
> CREATE TABLE `data_dedup_log` (
>   `id`          bigint unsigned NOT NULL AUTO_INCREMENT,
>   `point_id`    bigint unsigned NOT NULL,
>   `ts`          datetime(3) NOT NULL COMMENT '被判定重复的样本时间',
>   `dup_value`   decimal(16,4) NOT NULL COMMENT '被丢弃的值（留痕，不静默丢弃）',
>   `first_id`    bigint unsigned NOT NULL COMMENT '首次入库样本id',
>   `dedup_rule`  tinyint unsigned NOT NULL COMMENT '1同秒同值 2序号重复 3时间窗内重复',
>   `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP,
>   PRIMARY KEY (`id`), KEY `idx_point_ts` (`point_id`,`ts`)
> ) COMMENT='重复样本剔除留痕（FR-102 审计用）';
> ```
> 即：**允许同秒多条入库（保零丢失），再由清洗任务判定重复并留痕**，而不是靠唯一键"静默 IGNORE"。

## P0-5 分区无 `MAXVALUE` 兜底，建分区任务失败即当月数据全量写入失败

### 问题
附录 A DDL（L782-L786）与 3.5.1（L118）：分区为 `p202601 …` 逐月预建，**最后一个分区之后没有 `MAXVALUE` 兜底**。

### 原理/证据
MySQL 对 RANGE/RANGE COLUMNS 明确要求最后分区上界须覆盖所有可能值，否则插入超界报错：

```
mysql> CREATE TABLE t(a datetime NOT NULL, PRIMARY KEY(a))
       PARTITION BY RANGE COLUMNS(a) (PARTITION p0 VALUES LESS THAN ('2026-02-01'));
mysql> INSERT INTO t VALUES ('2026-02-01 00:00:00');
ERROR 1526 (HY000): Table has no partition for value from column_list
```

官方手册 [26.2.3.1 RANGE COLUMNS partitioning](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/partitioning-columns-range.html) 明确支持 `MAXVALUE`：

> "you can use `MAXVALUE` to represent a value such that any legal value inserted into a given column is always less than this value"
> `PARTITION p3 VALUES LESS THAN (MAXVALUE,MAXVALUE,MAXVALUE)`
> "there should be no more than one partition defined where MAXVALUE is used as the upper limit for all column values, and this partition definition should appear **last**"

### 后果
1. 3.5.1 的建分区任务是**应用内定时任务**（每月 1 日 00:10）。它一旦失败——服务未启动（Windows 服务被误停）、升级窗口覆盖、磁盘满、`ALTER TABLE` 元数据锁等待超时——**次月 1 日 00:00:00 起的每一条数据都插入失败**。
2. 失败模式是**静默累积**的：若接入层异常被 catch 后只记日志（架构文档 L213 提到背压时"丢弃旧数据并记数告警"，但未覆盖 DDL 失败），则现场出现"数据看板不动、无人知道原因"的灾难。等运维发现时，**该月所有原始数据已永久丢失**（网关上是否缓存取决于现场设备，不可依赖）。
3. 恰逢 FR-101 验收要求"连续 24h 数据零丢失"（L155）——这类故障必然在 30 天试运行期内被触发。

### 修复建议
```sql
-- 每个预建月分区之后，追加单一兜底分区（必须放在最后）
PARTITION pmax VALUES LESS THAN (MAXVALUE)
```
配套要求（写入文档）：
1. 应用侧对 `ERROR 1526` 做**独立告警通道**（不进背压降级逻辑），并自动触发"补齐分区"自愈动作；
2. 建分区任务改为**幂等 + 提前 3 个月**预建（`information_schema.PARTITIONS` 查重后 `ADD PARTITION`），且**必须在应用启动时执行一次**，而不是只在每月 1 日跑；
3. 每日巡检脚本校验 `pmax` 存在且 `MAX(PARTITION_ORDINAL_POSITION)` 分区上界 ≥ 当前日期 +90 天。

## P0-6 分区清理无边界算法，存在删除当月数据的实现路径

### 问题
3.9 数据生命周期（L721-L722）只写了一句"每日 03:00 任务：超期月份 `DROP PARTITION`"，L119 补充"过期数据归档后 `DROP PARTITION`（配合 3.9 生命周期任务）"。**没有任何一处给出 `DROP PARTITION` 的判定条件、分区名解析规则或边界值来源。**

### 后果（两种典型错误实现）
**错误实现 A（按分区名解析）：** 分区名 `p202601` → 解析出 `2026-01` → 与"当前月 −12 个月"比较。

```sql
-- 常见写法：用分区名字符串判断（危险）
ALTER TABLE data_sample DROP PARTITION p202601;
```

风险点：`RANGE COLUMNS` 分区的**语义是"上界"**。`p202601 VALUES LESS THAN ('2026-02-01')` 里装的是 **2026-01 整月**数据，但分区名读起来像"2026年1月1日"。"超期 1 年"的阈值一旦按"分区上界 ≤ 今天"或"分区名月份 ≤ 当前月 −12"实现，就会**多删一个月**。

**错误实现 B（先算出上界再比对）：** 若把 `2026-02-01` 当作 p202601 的"所属月"，则判定"2026-02 已超期"会在 2027-02 发生——此时 p202601 实际是 2026-01 数据，看似安全；但换成保留 1 年、上界 = 2027-02-01 的分区（p202702）会在 2027-02 被删，**删的正是当月分区**。

**恢复是不可能的：** `DROP PARTITION` 是 DDL，**不写 undo、不进 binlog 的 row 事件、无法通过 binlog 回滚**。若再叠加 P0-7（无 binlog 归档/无延迟从库），被误删的整月原始采样数据**永久不可恢复**（原始数据只此一份）。

### 修复建议
用 `information_schema.PARTITIONS` 的**真实上界**驱动，绝不用分区名：

```sql
-- ① 先查（只读，运维演练用）：列出可安全删除的分区
SELECT PARTITION_NAME, PARTITION_DESCRIPTION, TABLE_ROWS
FROM information_schema.PARTITIONS
WHERE TABLE_SCHEMA='tgaws' AND TABLE_NAME='data_sample'
  AND PARTITION_NAME <> 'pmax'
  -- 上界（分区描述）严格早于"当前月首日 - 保留月数"，即整个分区数据都已超期
  AND STR_TO_DATE(PARTITION_DESCRIPTION,'%Y-%m-%d %H:%i:%s.%f')
      <= DATE_SUB(DATE_FORMAT(CURDATE(),'%Y-%m-01'), INTERVAL 12 MONTH);
```

```sql
-- ② 删除前必须做的三重校验（写入清理任务代码，非可选项）
-- (a) 断言待删分区上界 < 当月首日（防止删到当月）
-- (b) 断言待删分区 TABLE_ROWS 已成功归档（读归档清单表 data_archive_log 校验行数）
-- (c) 把 DDL 语句 + 分区名 + 上界 + 行数 写入 data_archive_log（见下）后才执行
```

```sql
-- ③ 新增留痕表（当前设计完全缺失，是审计不通过的硬伤）
CREATE TABLE `data_archive_log` (
  `id`             bigint unsigned NOT NULL AUTO_INCREMENT,
  `table_name`     varchar(64)  NOT NULL COMMENT '被操作表',
  `partition_name` varchar(64)  NOT NULL COMMENT '分区名',
  `bound_value`    varchar(32)  NOT NULL COMMENT '分区上界（VALUES LESS THAN 原值）',
  `row_count`      bigint unsigned NOT NULL COMMENT 'DROP 前行数（来自 I_S.PARTITIONS）',
  `archive_path`   varchar(255) DEFAULT NULL COMMENT '归档文件路径',
  `archive_verify` tinyint unsigned NOT NULL DEFAULT 0 COMMENT '0未校验 1行数校验通过 2失败',
  `oper_type`      tinyint unsigned NOT NULL COMMENT '1归档 2DROP 3补建分区 4失败告警',
  `result`         tinyint unsigned NOT NULL DEFAULT 1 COMMENT '1成功 0失败',
  `fail_reason`    varchar(500) DEFAULT NULL,
  `operator`       varchar(32)  NOT NULL DEFAULT 'system' COMMENT 'system=定时任务',
  `create_time`    datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '执行时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_tbl_part_time` (`table_name`,`partition_name`,`create_time`),
  KEY `idx_create_time` (`create_time`)
) ENGINE=InnoDB COMMENT='分区归档/删除留痕（NFR-DATA1/2 审计证据）';
```

> 补充：文档 L118"预建当年+次年共 24 个分区"与 L722"聚合表保留 3 年"**数量不匹配**——聚合表 3 年需要 ≥36 个月分区 + 兜底。见 P0-3。

## P0-7 RPO≤24h 与备份设计不匹配；"预警事件永久保留"与 MySQL 8.0 EOL 冲突

### 问题
3.10（L728-L734）：
- 备份方式：`mysqldump --single-transaction --default-character-set=utf8mb4` 全量逻辑备份（L730）；
- 备份计划：每日 02:00（L731）；
- 保留：最近 3 代 + 每周 1 代（L732）；
- 声明：**RPO ≤24h、RTO ≤2h**（L733）。

**未出现**：binlog、增量备份、`--master-data` / `--source-data`、PITR（时间点恢复）、异地/离线介质、备份校验（`restore.bat` 只"校验行数"，L733）。

### 原理/证据
1. **RPO 的实际含义**：仅靠每日 02:00 全量备份，最坏情形（磁盘故障发生在 01:59）丢失 **23小时59分**数据；若当日备份任务失败（磁盘满是最常见原因，而 L732 磁盘水位告警阈值只到 85%），下一次成功备份是 48 小时后 → **实际 RPO = 48h**，超出声明一倍。**没有 binlog 就没有 PITR，RPO 无法被压缩到 24h 以内**。
2. 需求 RPO 的真正约束（L301 永久保留、L423 单点故障风险 R6"单机部署可用性风险"，应对措施仅"每日自动备份"）——**单点 + 无 binlog + 无异地副本 = 磁盘损坏即丢失全部历史预警事件**，与"预警事件永久保留"（NFR-DATA3）**逻辑上不可同时成立**。
3. **RTO ≤2h 不可信**：按 §P0-9 修正后的真实容量（基线 1000 点×30s 约 150GB/年原始 + 聚合 + 索引），压缩后备份档约 25-40GB。`restore.bat` 走"解密→建库→导入→校验行数"，单线程 `mysql < dump.sql` 的**索引重建发生在导入过程中**（非 `--disable-keys` 批量重建），Windows 单机磁盘的实际恢复速率约 5-15GB/h 有效数据 → **恢复需 3-8 小时**，RTO 2h 无法达成。
4. **`--single-transaction` 对分区表 + 长事务的风险未评估**：全量 dump 期间会持有一致性快照读，与 01:00 分钟聚合任务（L731 提到"避开 01:00 聚合高峰"，说明已知冲突）叠加时，长事务 + 大 undo 可能拖慢在线写入；文档未设定 `--single-transaction` 之外的超时/限速策略。
5. **备份加密密钥与备份同机存放**：`${BACKUP_KEY}` 由初始化脚本生成（L835），备份文件也落本机 `backup\`（架构 L291）。磁盘/整机失窃或勒索加密场景下，**加密与密钥同时丢失 → 备份等于没有**（NFR-S6"备份文件加密"形式上满足、实质上无效）。
6. **MySQL 8.0.46 已于 2026-04 EOL**（需求文档 L425 风险 R8 自己已识别；0 号文档 L110 也已提示），但数据库设计说明书**通篇未提及升级路径与 EOL 对"永久保留"的影响**。等保二级 NFR-S1 要求"入侵防范"，一个不再获得安全补丁的数据库版本在测评中会被直接质疑。

### 修复建议
| 项 | 修订后设计 |
|---|---|
| 备份链 | `mysqldump` 全量（每周日 02:00）+ **binlog 增量 + PITR（每日 02:00、12:00 各一次 `mysqlbinlog` 归档，保留 7 天）** |
| MySQL 参数 | `log_bin=ON`、`binlog_format=ROW`、`binlog_row_image=MINIMAL`、`binlog_expire_logs_seconds=604800`、`sync_binlog=1` |
| 恢复目标 | RPO ≤ 12h（明确写成"备份周期×2 + binlog 归档间隔"的推导），RTO ≤ 4h（按实测恢复速率反推磁盘规格） |
| 备份校验 | `restore.bat` 增加：① 表数量比对（35/实际）② 关键表行数比对 ③ 抽样 10 行 `CHECKSUM TABLE` 比对 ④ 恢复后 `ANALYZE TABLE` 统计信息重建；结果写 `sys_backup_log` 新增字段 |
| 密钥管理 | 备份文件与 `${BACKUP_KEY}` 分离存放（密钥交由甲方保管、或写入 Windows 凭据管理器），备份目录纳入 U 盘/异地介质轮换（周备份） |
| EOL 处置 | 在本文档增补"版本与生命周期"章节：明确 8.0.46 停止支持日期、8.4 LTS 升级窗口（建议试运行结束前完成）、升级前的全量回归清单 |
| `sys_backup_log` 补字段 | `row_count`、`table_count`、`md5`、`binlog_file`、`binlog_pos`、`verify_result`、`expire_date` |

```sql
ALTER TABLE `sys_backup_log`
  ADD COLUMN `table_count`   int unsigned    NOT NULL DEFAULT 0 COMMENT '备份表数量' AFTER `file_size`,
  ADD COLUMN `row_count`     bigint unsigned NOT NULL DEFAULT 0 COMMENT '关键表总行数' AFTER `table_count`,
  ADD COLUMN `md5`           char(32)        DEFAULT NULL COMMENT '备份文件校验值' AFTER `row_count`,
  ADD COLUMN `binlog_file`   varchar(64)     DEFAULT NULL COMMENT '对应binlog文件（PITR起点）' AFTER `md5`,
  ADD COLUMN `binlog_pos`    bigint unsigned DEFAULT NULL COMMENT '对应binlog位点' AFTER `binlog_file`,
  ADD COLUMN `verify_result` tinyint unsigned NOT NULL DEFAULT 0 COMMENT '0未校验 1通过 2失败' AFTER `binlog_pos`,
  ADD COLUMN `expire_date`   date            DEFAULT NULL COMMENT '本代备份过期日期（滚动清理依据）' AFTER `verify_result`;
```

## P0-9 容量模型可信度审查：口径自相矛盾，500GB 余量严重不足

### 问题
3.12（L754-L759）：

```
年存储量 ≈ 日均条数 D × 单行字节 B × 365 × 1.4（索引/页开销）
| 基线（需求口径） | 100 万（B≈100B） | ≈51GB | ≈55GB（B≈50B） | ≈40GB | ≥500GB（与架构文档一致，5 倍余量） |
| 上限（5000 点×30s 全开） | 1440 万 | ≈736GB | ≈790GB | ≈80GB | ≥2TB |
```

### 问题 1：基线口径与 FR-101 验收条件**直接矛盾**
- 需求 L79/L82：采集频率 **30s~5min**；L77-L82 六大对象中"坍塌/涌水/瓦斯/突泥"四类均标注 **30s~5min**。
- FR-101 验收（L155）："模拟网关推送 **1000 点、30s 周期**连续 24h，数据零丢失"。

按此计算基线应为：**1000 点 × 2880 条/天 = 288 万条/天**，而非文档的 100 万条/天。
文档"上限"行自己写的"5000 点×30s 全开 = 1440 万"（5000×2880 = 1440 万 ✓ 算术正确），反证 1000 点 30s 全开 = **288 万**。**基线被低估 2.88 倍**，且这个低估的口径来源（"需求口径"）在需求文档中查无实据。

### 问题 2：单行字节估算偏低
InnoDB DYNAMIC 行格式精算 `data_sample`（现设计）：

| 组成 | 字节 |
|---|---|
| 行头（变长字段长度列表 2 + NULL 位图 1 + 记录头 5 + 事务 id 6 + 回滚指针 7） | 21 |
| `id` bigint | 8 |
| `point_id` bigint unsigned | 8 |
| `ts` datetime | 5 |
| `value` decimal(16,4) （16 位十进制 → 4 字节整数部分 + 4 字节小数部分 = 8） | 8 |
| `quality` + `source` tinyint unsigned | 2 |
| `receive_time` datetime | 5 |
| **聚簇索引单行合计** | **≈57** |
| `idx_point_ts(point_id, ts)` 二级索引项（8+5+主键 id 8+主键 ts 5+记录头 6） | **≈32** |
| **行 + 全部索引项** | **≈89** |
| B-tree 页填充因子（约 15/16）与页头/目录开销（≈1.6~1.8×） | → **实际 ≈145~160 B/行** |

结论：文档 `B≈100B` 是**裸行估算未计索引页放大**；`×1.4` 系数单独看**接近正确**（89×1.4 ≈125），但它与 `B=100B` **重复计算/口径混乱**——若 B 已含索引则 1.4 是双重放大（此时 51GB 偏保守），若 B 不含索引则 1.4 不足（真实 ≈89/57 = **1.56**）。文档未说明 B 的口径，**无法验证**，这是评审必须打回的表述缺陷。

同时指出**跨文档数字冲突**：架构文档 L342 用"~120B/条"算出"1 年 ≈44GB"（未乘 1.4），3.12 用"100B×1.4"算出"≈51GB"。**同一份数据量给出两个不同字节数与两个不同容量值**，两文档未对齐。

### 问题 3：聚合表"3 年 ≈55GB"低估约 1 倍，且"≤原始量"表述不成立
- 聚合表 3.6.4 无 DDL（P0-3），但字段表（L411-L420）有 8 列：`id`(8) + `point_id`(8) + `ts_minute`(5) + 3×decimal(16,4)(24) + `sample_count` int(4) + `quality_ratio` decimal(5,4)(3) + 行头(21) ≈ **73 B 裸行**。
- 按 30s 采集，**每个点位每分钟产出 1 行聚合**（2 个原始样本 → 1 行），聚合行数 = 原始行数 ÷ 2 = 144 万行/天（基线 288 万口径）。
- 3 年 = 15.8 亿行 × 73 B ≈ **115 GB 裸数据**，加索引 ≈ **135~150 GB**。
- 文档写 **55GB** → **低估 2.5 倍**。
- "≤原始量"（L96）在 30s 频率下勉强成立（1/2），但若按文档基线 100 万条/天反推，聚合也是 100 万行/天（1/1），55GB 仍不足。

### 问题 4：完全遗漏的容量项
| 遗漏项 | 量级估算（Windows 单机、8C16G） |
|---|---|
| **binlog** | ROW 格式 + `binlog_row_image=FULL`，每行 insert ≈200~300 B → 基线 288 万条/天 ≈ **600~900 MB/天**；保留 7 天 ≈ **4~6 GB**；若开 MINIMAL 约减半。**文档 3.12 与 3.10 均未提 binlog**，也未提其与 RPO 的关系（见 P0-7） |
| **redo log** | `innodb_log_file_size` 默认 48MB×2 = 96MB，建议调至 1~2GB×2 以提升写入吞吐 → **2~4 GB** |
| **undo 表空间** | 长事务（大导出、分钟聚合、mysqldump 一致性快照）会撑大 undo → 建议预置 **4~8 GB** 上限并配 `innodb_max_undo_log_size` |
| **临时表空间** | 报表 `GROUP BY` 3 年聚合表时，磁盘临时表可轻易超过 `tmp_table_size` → **10~30 GB** 波动 |
| **ibdata1 / 系统表空间** | 1~2 GB |
| **业务文件** | 巡检/处置照片（每条 1~3 张、每张 1~3MB）、导出文件、归档包、报告 → 3 年 **30~80 GB** |
| **MySQL 二进制与日志** | error log / slow log / 归档 **5~10 GB** |
| **备份保留 4 代的峰值** | 压缩比约 3~4:1 → 基线 3 年数据压缩后约 80~120 GB，4 代峰值 **160~240 GB**（若按架构 L291"保留 3 代滚动"+每周 1 代 = 4 代） |
| **小计** | **≈ 215~380 GB（不含备份）/ 375~620 GB（含备份）** |

### 问题 5：500GB 与"5 倍余量"的结论**不成立**

按 FR-101 验收口径（1000 点×30s）重算：

| 项 | 计算 | 结果 |
|---|---|---|
| 原始表 1 年 | 288 万 × 150 B × 365 | **≈158 GB** |
| 聚合表 3 年 | 144 万 × 100 B × 365 × 3 | **≈158 GB** |
| 业务表 + 文件 3 年 | — | ≈30~50 GB |
| MySQL 内部开销（binlog/redo/undo/临时） | 见问题 4 | ≈20~45 GB |
| 备份 4 代（压缩） | — | ≈150~200 GB |
| **合计** | | **≈515~610 GB** |

→ **≥500GB 在需求自证的验收口径下已经不够用**，"5 倍余量"实际是 **0.8~1.0 倍**（负余量）。
→ 若 5000 点×30s（1440 万/天）上限：原始 736GB（文档值，本审计按 150B 修正为 **≈789 GB**）+ 聚合 790GB（修正 **≈789 GB**）+ 备份与开销 → **≈2.2~2.6 TB**，文档"≥2TB"同样不足。

### 问题 6：缓冲池与内存口径
- `innodb_buffer_pool_size=8G` 占 16G 的 50%，**对"近 3 天采样 + 全部业务表"的热数据（约 1.5~3 GB）足够**，结论方向正确。
- **但未论证跨分区历史查询的 I/O 成本**：查 6~12 个月前的曲线时，数据不在缓冲池，命中 `idx_point_ts` 后仍需**每次回表一次随机 I/O**（P1-1）。在 Windows 单机磁盘（通常无 SSD 或仅 SATA SSD）上，若一次查询返回 2000~5000 行，回表 I/O 达数千次随机读 → **P95≤3s 不达标**。
- **未列出关键 InnoDB 参数**：`innodb_flush_log_at_trx_commit`、`innodb_io_capacity`、`innodb_log_file_size`、`sync_binlog`、`innodb_flush_method`（Windows 下应设 `unbuffered` 或 `normal`，默认 `fsync` 在 Windows 上性能最差）、`innodb_adaptive_hash_index`、`tmp_table_size`、`max_heap_table_size`。架构 L355 只说"批量提交、日志落盘策略"，**无具体值即无法验收**。

### 修复建议
1. **重算并统一口径**（建议基线取 FR-101 验收条件）：

2. **磁盘建议值上调**：基线 **≥2TB NVMe SSD**（含备份与 3 年增长），上限场景 **≥4TB** 或缩短原始保留期至 6 个月 / 二期迁时序库。500GB 仅够 1 年且不含备份。

### 真正的问题（三条，均可验证）
1. **口径未定义 → 无法判定合规**。3.2 写"单表索引 ≤5 个"，附录 A 又用"4 个（不含主键）"来自证合规。同一文档对"索引个数"是否含主键给出两个口径。若含 PK，`mon_point` = **5** 恰好压线、`warn_event` = **5** 恰好压线——**零余量**，任何后续新增索引（例如 P0-8 要求补的 `manual_flag`/`archive_status` 索引）立即超标。

3. **存在冗余/低效索引**（与"禁止重复索引与冗余索引"自相矛盾）：
   - `mon_point.idx_hazard(hazard_type)`：`hazard_type` 只有 **6 个取值**、5000 行表——选择度 1/6，优化器**几乎不会**选择该索引；它占位一个"索引名额"却几乎无用。应删除，或改造为 `(hazard_type, tunnel_id)` 而由 `idx_tunnel_section` 覆盖隧道维度。

## P1-1 主键与聚簇索引：`(id, ts)` 与查询模式错配，回表放大

### 问题
- 主键 `PRIMARY KEY(id, ts)`（L407，`id` 为雪花）；查询模式是"**按 point_id + 时间范围查曲线**"（L706、L168 FR-203）；
- `idx_point_ts(point_id, ts)` 是二级索引（L407）。

### 原理/证据：回表开销量化
InnoDB 二级索引叶子节点存的是 **索引列 + 主键列**。因此 `idx_point_ts` 的叶子项是 `(point_id, ts, id, ts)`。执行：

```sql
-- 查 1 个点位 1 小时曲线（30s 周期 → 120 行）
SELECT ts, value FROM data_sample
WHERE point_id = 88 AND ts >= '2026-03-01 00:00:00' AND ts < '2026-03-01 01:00:00'
ORDER BY ts;
```

执行代价（`EXPLAIN` 可见 `type=range, key=idx_point_ts, Extra=Using index condition`）：
1. 在 `idx_point_ts` 上**范围扫描 120 项**（分区裁剪后落在 1 个月分区内，若跨月则扇出为 N 个分区各自的局部索引）；
2. 对每一项，用其中的 `(id, ts)` 去**聚簇索引（主键 B-tree）查一次完整行**取 `value`、`quality`、`source`；
3. 因为聚簇键首列是**雪花 id（随机、单调递增但跨点位交错）**，120 个 `(id, ts)` 在聚簇 B-tree 中**互不相邻** → **120 次随机 I/O**（缓冲池未命中时）。

量化：查 24 小时曲线 = 2880 行 → 2880 次随机回表。Windows 机械盘 ≈100 IOPS → **28 秒**；SATA SSD ≈5000~20000 IOPS → 0.15~0.6s（勉强）；而**跨分区历史查询（6~12 个月前）必然缓冲池不命中**。多测项对比（FR-203 "多测项曲线对比"，如 6 个测项 × 24h）→ 回表 17280 次 → **机械盘 3 分钟，SSD 也要 1~3.5s**，与 **P95≤3s 只差一线**。若断面级对比（20~50 个测项），**必然超标**。

另外，分区表上每个分区有**独立的局部索引**：`idx_point_ts` 在 12 个月分区里就是 **12 棵独立的 B-tree**。跨年查询时优化器需对每个分区分别做 range scan 再归并，"一个索引"实际是一次**分区扇出 × 索引查找**。

### 后果
- FR-203"100 万条数据量级查询 P95 ≤3s"（L168）在单测项场景勉强达标，在 FR-203 明确要求的"**多测项曲线对比**"与 FR-202"断面图"场景**大概率超标**；
- 随数据增长（第 6~12 个月）性能持续劣化，试运行 30 天期间恰好是数据量最小的窗口 → **验收通过、上线后 6 个月不达标的典型模式**。

### 修复建议：聚簇键改为 `(point_id, ts)`
```sql
-- 改造后：曲线查询变成聚簇索引上的顺序区间扫描，零回表
PRIMARY KEY (`point_id`, `ts`),
-- idx_point_ts 可删除（聚簇键已覆盖其前缀语义）
KEY `idx_ts` (`ts`)          -- 仅用于"全断面/全线按时间"的聚合任务与归档校验
```

收益（针对改造后的表结构重算）：

| 场景 | 现设计 | 改造后 |
|---|---|---|
| 单点 24h 曲线（2880 行） | idx 扫描 2880 项 + 2880 次随机回表 | 聚簇顺序扫描 2880 行，**~10 次页读** |
| 单点 1 年曲线（105 万行） | ~105 万次随机回表（不可行） | 顺序扫描，可流式返回 |
| 跨分区查询 | N 个分区 × 局部索引扇出 | N 个分区 × 顺序扫描，无扇出放大 |
| 写入 | 主键随机插入（雪花乱序）→ 页分裂 | 按 (point_id, ts) 近似顺序插入 → **页分裂显著减少** |
| 空间 | 主键 8+5=13 B/行，二级索引 8+5+8+5=26 B | 主键 8+5=13 B/行，省掉 26 B 二级索引项 → **单行省约 26 B（≈23%）** |

> ⚠️ **改造代价（必须写进文档）**：`ALTER TABLE ... DROP PRIMARY KEY, ADD PRIMARY KEY(...)` 在**分区表上是 INPLACE 重建**（copy 算法），需按分区或整表重建。基线 1.58 亿行（1 年）重建在 8C16G 单机上预计 **2~6 小时**，且需 1.6 倍磁盘余量。**因此必须在上线前定稿，不能等到有数据再改**——这是本审计最关键的时序性结论。

### 「雪花 id 还需要吗？」
**不需要，建议删除 `id` 列。** 理由：
1. 改造后 `(point_id, ts)` 已是稳定、唯一、且**有序**的主键——具备优秀的聚簇局部性，正是雪花 id 想解决的问题（分布式有序主键），而本系统是**单库单写入方**，无需分布式主键。
2. 雪花 id 反而**破坏**聚簇局部性（跨点位交错），是 P1-1 回表问题的根因之一。
3. 每行省 8 B 主键 + 6 B 记录头，二级索引项省 8 B → 1 年 1.58 亿行节省 **≈3.5 GB**，写入 CPU 省去每行一次雪花生成。

### 「会不会出现主键冲突？」
分三种情况：
1. **保留雪花 id（`(id, ts)`）**：理论冲突概率极低，但**不归零**——雪花依赖时钟单调性，**NTP 回拨 / 手动改系统时间 / 虚拟机挂起恢复**都会造成重复 id。Windows 单机 + 现场无可靠 NTP 时，这是**真实风险**。而 `(id,ts)` 联合主键会把冲突从"id 冲突"变成"(id,ts) 冲突"，反而**掩盖**问题（同一 id 配不同 ts 可以共存，破坏唯一性语义）。
2. **改为 `(point_id, ts)`**：冲突条件变为"同一点位同一时刻",这**正是业务去重语义**。需要注意：`datetime` 秒级下确实可能冲突（P0-4），因此**必须同时提升到 `datetime(3)`**。
3. **与 P0-4 的联动结论**：改为 `(point_id, ts(3))` 主键后，**不要**用 `INSERT IGNORE` 处理冲突（会静默丢数），而应：
```sql
-- 显式处理：冲突时保留原始值并写去重留痕（FR-102 可审计）
INSERT INTO data_sample (point_id, ts, value, quality, source, sample_seq, receive_time)
VALUES (?,?,?,?,?,?,NOW(3))
ON DUPLICATE KEY UPDATE
  `value` = VALUES(`value`),      -- 或保留首值（按业务定稿）
  `quality` = LEAST(`quality`, VALUES(`quality`)),
  `receive_time` = VALUES(`receive_time`),
  `sample_seq` = VALUES(`sample_seq`);
-- 同事务内按 affected rows = 2 判定"发生了重复"，另写 data_dedup_log
```
4. **`warn_event.trigger_value` 的关联链路会断**：现设计下 `warn_event` 通过"触发值快照"关联样本；若删掉 `data_sample.id`，需改为 `(point_id, trigger_time)` 定位——**这是必须同步修订的引用契约**（P0-8 已列此项）。

## P1-2 逻辑删除与唯一索引冲突

### 问题
3.2（L33）要求业务表统一含 `is_deleted tinyint unsigned`。而以下唯一键**不含** `is_deleted`：
`sys_user.uk_username`（L152）、`sys_role.uk_role_code`（L163）、`mon_point.uk_point_code`（L369）、`mon_rule.uk_rule_code`（L391）、`prd_section.uk_tunnel_section`（L344）、`sys_dict_type.uk_dict_code`（L205）、`sys_config.uk_config_key`（L228）、`sys_third_app.uk_app_key`（L286）、`sys_notify_channel.uk_channel_code`（L273）、`sys_schema_version.uk_version`（L310）、`data_import_batch.uk_batch_no`（L452）、`warn_dispose_task.uk_task_no`（L514）、`patrol_*` 各 `uk_*_no`、`rpt_*` 各 `uk_*_no`、`ai_model.uk_model_version`（L637）。

### 后果（逐条可验证）
**① 删除后编码永久不可复用** → `mon_point.point_code` 是"**报文匹配键**"（L352）。现场更换传感器/改点位编号时：
```sql
-- 停用旧点（逻辑删除）
UPDATE mon_point SET is_deleted = 1 WHERE point_code = 'CH4-001';
-- 新点位沿用同一编码（现场标签未改、或网关配置未改）
INSERT INTO mon_point (point_code, ...) VALUES ('CH4-001', ...);
-- ERROR 1062 (23000): Duplicate entry 'CH4-001' for key 'mon_point.uk_point_code'
```
→ 运维必须直接连库改名，或新增 `CH4-001-2` 之类的"脏编码"，**破坏编码与现场物理标签的一致性**，FR-101"报文匹配键"随之失效。

**② 更危险的静默错行（比报错更糟）**：若应用层对点位/用户的查询**未过滤 `is_deleted`**（这是最常见的实现疏漏），则逻辑删除后：
- 数据接入按 `point_code` 查点位 → 命中**已删除的那一行** → 数据挂到废弃 `point_id` 上 → **看板永远不显示、预警永不触发**，而数据"看起来入库成功"。这是**最隐蔽的数据事故**：FR-101 的"零丢失"形式上满足，业务上完全丢失。
- 登录按 `username` 查用户 → 命中已删除用户 → 若只校验密码则可**用已注销账号登录**（等保二级"身份鉴别"直接不通过）。

**③ 唯一索引空间永久占用**：逻辑删除行不释放索引项，`uk_point_code` 随删除累积膨胀，长期影响该索引的页密度。

### 修复建议（推荐方案：`deleted_at` 时间戳替代 `is_deleted`）
```sql
-- 统一改造：is_deleted tinyint → deleted_at datetime NULL
-- MySQL 唯一索引对多个 NULL 视为互不相等，因此"活跃行 deleted_at IS NULL"天然唯一
ALTER TABLE `mon_point`
  ADD COLUMN `deleted_at` datetime DEFAULT NULL COMMENT '逻辑删除时间，NULL=未删除' AFTER `is_deleted`;

-- 唯一键包含 deleted_at：同一编码仅 1 个活跃行 + 任意多个历史删除行
ALTER TABLE `mon_point`
  DROP INDEX `uk_point_code`,
  ADD UNIQUE KEY `uk_point_code` (`point_code`, `deleted_at`);

-- 删除改为写时间戳（可精确到毫秒，避免同一秒删除两次冲突）
UPDATE mon_point SET deleted_at = NOW(3) WHERE id = ?;
-- 应用层查询统一改为 … WHERE deleted_at IS NULL
```
> 依据：MySQL 唯一索引允许多个 NULL 值（`InnoDB: UNIQUE IF NOT NULL` 语义），因此 `(point_code, NULL)` 可重复出现任意次，而 `(point_code, 非NULL)` 各自唯一。

**必须同步执行的配套项**：
1. **所有唯一键覆盖改造**（至少 `sys_user`、`mon_point`、`mon_rule`、`sys_config`、`sys_dict_type`、`sys_third_app`、`sys_notify_channel`、`prd_section`）；
2. **接入/登录等关键路径禁止依赖 `is_deleted` 过滤**，必须显式 `deleted_at IS NULL`；
3. **`deleted_at` 与唯一键组合需回归校验**：`uk_point_code(point_code, deleted_at)` 后的**删除→重建→再删除**三次操作序列必须通过（这是最容易被忽略的边界）；
4. 若坚持 `is_deleted tinyint`，则唯一键必须改为 `(code, is_deleted)` —— **但这只允许"删除 1 次"**（第二次删除冲突），属于**不完整方案**，不推荐。

## P1-3 审计日志"不可删改"无技术保障

### 问题
需求 L219（FR-704）："全操作审计日志……可查询、**不可删改**、保留 ≥6 个月"。
架构 L317（等保二级安全审计）："保留 ≥6 个月，**独立审计表防篡改（仅追加）**"。
数据库设计：`sys_oper_log`（L230-L245）、`sys_login_log`（L247-L259）**只是普通 InnoDB 表**，除"无 `is_deleted`"外**没有任何防篡改机制**。

### 后果
1. 应用使用的 DB 账号（`${DB_USERNAME}`，L832）为了写业务数据必然是 `SELECT/INSERT/UPDATE/DELETE` 全权限；**任何能连库的人都能 `UPDATE sys_oper_log SET operation='...'` 或 `DELETE FROM sys_oper_log`**。
2. 等保二级测评项"安全审计"要求审计记录**防未预期的删除、修改、覆盖**。现设计**形式上有一条"仅追加"的文字说明，技术上零落地**——测评时属于**直接不符合项**。
3. 无数据库账号分离、无权限回收、无审计日志自身的变更留痕（"谁删了日志"不可追溯），也**无 binlog 归档**（P0-7）作为交叉验证。审计日志被删后**无法察觉、无法恢复**。

### 修复建议（三层，缺一不可）
```sql
-- 第 1 层：账号分离与最小权限（写入 scripts/db/schema/00_create_db.sql）
-- 应用账号：业务表全权限，审计表仅 INSERT+SELECT
CREATE USER 'tgaws_app'@'localhost' IDENTIFIED BY '${DB_USERNAME}';
GRANT SELECT, INSERT, UPDATE, DELETE ON tgaws.* TO 'tgaws_app'@'localhost';
REVOKE UPDATE, DELETE ON tgaws.sys_oper_log   FROM 'tgaws_app'@'localhost';
REVOKE UPDATE, DELETE ON tgaws.sys_login_log  FROM 'tgaws_app'@'localhost';
REVOKE UPDATE, DELETE ON tgaws.warn_event_timeline FROM 'tgaws_app'@'localhost';
REVOKE UPDATE, DELETE ON tgaws.warn_event_level_log FROM 'tgaws_app'@'localhost';
REVOKE UPDATE, DELETE ON tgaws.data_archive_log     FROM 'tgaws_app'@'localhost';
REVOKE DELETE ON tgaws.warn_event FROM 'tgaws_app'@'localhost';  -- 预警事件永久保留

-- 审计查询账号（仅给系统管理员角色，且其登录本身被审计）
CREATE USER 'tgaws_audit'@'localhost' IDENTIFIED BY '${DB_AUDIT_PASSWORD}';
GRANT SELECT ON tgaws.sys_oper_log, tgaws.sys_login_log TO 'tgaws_audit'@'localhost';
```
```sql
-- 第 2 层：哈希链（检测篡改，成本极低，30 行内可实现）
ALTER TABLE `sys_oper_log`
  ADD COLUMN `prev_hash` char(64) DEFAULT NULL COMMENT '上一条记录哈希（链式防篡改）' AFTER `oper_time`,
  ADD COLUMN `row_hash`  char(64) NOT NULL COMMENT '本条记录哈希=SHA256(前序字段||prev_hash)' AFTER `prev_hash`;
-- 应用层计算；每日 03:00 校验任务重算全链，断链即告警并写 sys_config 告警位
```
```sql
-- 第 3 层：独立归档（保留 ≥6 个月 + 防覆盖）
-- 每日 03:30 将 30 天前的 oper_log 导出为只读文件（AES 加密）存 archive/ 并写 data_archive_log；
-- 归档文件生成后置 Windows 只读属性 + 记录 md5；保留期按 NFR-S4 ≥6 个月，建议 2 年
```
> 同时：文档 L68 说"审计类表不用逻辑删除"，但 L723 又说"审计日志 ≥6 个月后可归档"——**归档 = 物理删除**，这两句需明确区分"行保留"与"归档后删除"的边界，并给出归档任务的时间、校验与留痕要求（当前完全没有）。

## P1-4 统计报表/驾驶舱（FR-801/802）无可落库指标，P95≤3s 无支撑

### 问题
FR-801（L226）要求"日/周/月报：预警统计、**处置闭环率**、**数据完整率**、**巡检完成率**"；FR-802（L227）要求驾驶舱"**今日预警、闭环率、高风险点位、设备在线率**，指标实时刷新 ≤1min"。

数据库设计中**没有任何一张统计/指标表**（3.4 总览 35 张表逐条核对：`rpt_report` 只存报告文件路径，`rpt_export_task` 只存导出任务）。所有指标都必须**实时聚合**。

### 后果（可量化的查询灾难）
```sql
-- FR-801 "数据完整率"：必须逐点位逐分钟比对期望样本数与实际样本数
-- 基线 1000 点、聚合表 3 年 15.8 亿行（P0-9 修正值）
SELECT p.tunnel_id,
       SUM(m.sample_count)                                   AS actual,
       SUM(m.expect_count)                                   AS expect,
       ROUND(SUM(m.sample_count)/SUM(m.expect_count)*100,2)  AS complete_rate
FROM data_sample_minute m JOIN mon_point p ON p.id = m.point_id
WHERE m.ts_minute >= '2026-01-01' AND m.ts_minute < '2026-02-01'   -- 一个月 = 4320 万行
GROUP BY p.tunnel_id;
```
单月查询需扫描 **4320 万行**并做分组聚合。缓冲池只有 7~8 G（P0-9 问题 6），必然落盘临时表，Windows 单机预计 **30~180 秒**。而"指标实时刷新 ≤1min"（FR-802）**要求 60 秒内返回**——**架构上不可能**。

其余三个指标同样问题：
- **闭环率**：需扫 `warn_event`（`warn_status=5` 计数）——1 万行/年尚可，但"按级别×时间×隧道"多维分组时会全表扫描；
- **设备在线率**：现设计**根本没有心跳表**（P0-8 缺口），只能靠 `mon_point.last_data_time` 反推，而 `last_data_time` 是 `datetime` 且**无索引**（L366，索引只有 4 个，无 `last_data_time`）→ 5000 行全扫尚可，但**语义错误**（"最近有数据"≠"在线"，采集周期 1800s 的点位会被误判离线）；
- **高风险点位**：需 `warn_event` JOIN `mon_rule` JOIN `mon_point` 实时算，无预计算。

### 修复建议
1. **新增 `rpt_stat_daily`**（DDL 见 §P0-8.1 ⑤），由**每日 00:30 定时任务**在低峰期预计算，报表与驾驶舱**只查这张表**（365 行/年，查询 <10ms）。
2. 驾驶舱"今日"指标走一张 `rpt_stat_realtime`（内存态 + Caffeine 缓存，5s TTL，架构 L353 已规划 Caffeine），**不落库**；每小时落一次快照以便追溯。
3. FR-801 要求"**报表数据与台账核对一致**"（L226 验收要点）——预计算表必须**保留计算时的 SQL 与源表行数快照**，否则无法对账。建议 `rpt_stat_daily` 增加 `calc_sql_hash`、`source_row_count`、`calc_cost_ms`。
4. 报告生成任务改为**读取 `rpt_stat_daily`** 而非实时聚合，`rpt_report` 增加 `summary_json`（存当期指标值，便于"报告与台账核对"）。

## P1-5 索引缺陷：重试查询与报表查询走不到索引

### 问题 1：`warn_notify_log` 无法高效支持重试
FR-304（L178）与架构 L255 要求"发送失败**重试**"。
现索引（L498）：`idx_event(event_id)`、`idx_send_time(send_time)`。
重试扫描的查询是"**status 为失败/重试中、且未超过最大重试次数**的待重发记录"：
```sql
SELECT * FROM warn_notify_log
WHERE status IN (2,3) AND retry_count < 3 AND send_time <= NOW() - INTERVAL 1 MINUTE
ORDER BY send_time LIMIT 100;
```
- `idx_send_time` 只有 `send_time`，`status`/`retry_count` 需**回表过滤**；失败记录本就是少数（假设 5%），5 万行/年 × 5% = 2500 行/年——**看似不多**，但该查询**每分钟执行一次**（重试轮询），每次回表 2500 次 → 每日 360 万次随机 I/O。这是**典型的"表不大但查询频率极高"的隐性性能黑洞**。
- 更糟的是 `idx_event` 与 `idx_send_time` **都不支持该查询的最左前缀**，优化器可能直接选 `idx_send_time` 范围扫描 → 扫到全月数据。

**修复**：
```sql
ALTER TABLE `warn_notify_log`
  DROP INDEX `idx_send_time`,
  ADD KEY `idx_status_retry` (`status`,`retry_count`,`send_time`),  -- 覆盖重试扫描
  ADD COLUMN `next_retry_time` datetime DEFAULT NULL COMMENT '下次重试时间' AFTER `retry_count`,
  ADD COLUMN `event_no` varchar(32) NOT NULL COMMENT '事件编号快照（无需回表关联）' AFTER `event_id`,
  ADD COLUMN `template_id` bigint unsigned DEFAULT NULL COMMENT '通知模板id' AFTER `event_no`,
  ADD COLUMN `provider_msg_id` varchar(64) DEFAULT NULL COMMENT '供应商回执消息号（送达凭证）' AFTER `fail_reason`,
  ADD KEY `idx_next_retry` (`next_retry_time`);
-- 重试查询改为：WHERE status = 2 AND next_retry_time <= NOW() → 索引精确命中
```

### 问题 2：`patrol_record` 缺报表所需索引
现索引（L598）：仅 `idx_task(task_id)`。但 FR-801"巡检完成率"、FR-802 需要按时间统计：
```sql
SELECT DATE(record_time), COUNT(*) FROM patrol_record
WHERE record_time >= ? AND record_time < ? GROUP BY DATE(record_time);   -- 全表扫描
```
10 万行/年 × 3 年 = 30 万行——单次扫描可接受（<1s），但**驾驶舱每分钟刷新**（FR-802）→ 每分钟一次 30 万行扫描，与在线聚合任务抢 I/O。且 `patrol_record` **缺 `tunnel_id`/`inspector_id` 冗余字段**，无法按隧道/人员维度统计（需 JOIN `patrol_task`，而 JOIN 键 `task_id` 索引可用但会放大行数）。

**修复**：
```sql
ALTER TABLE `patrol_record`
  ADD COLUMN `tunnel_id` bigint unsigned NOT NULL COMMENT '隧道id（冗余，报表统计用）' AFTER `task_id`,
  ADD COLUMN `inspector_id` bigint unsigned NOT NULL COMMENT '巡检人id（冗余）' AFTER `recorder_id`,
  ADD KEY `idx_record_time` (`record_time`),
  ADD KEY `idx_tunnel_time` (`tunnel_id`,`record_time`),
  ADD UNIQUE KEY `uk_task_item` (`task_id`,`item_id`);   -- 见 P1-x：防重复填报
```

### 问题 3：`sys_oper_log` 审计查询缺索引
FR-704 要求"可查询"日志。运维/审计实际查询是"**某模块某时段的操作**"：
```sql
SELECT * FROM sys_oper_log WHERE module = '预警管理' AND oper_time >= ? AND oper_time < ?;
```
现索引（L245）：`idx_oper_time(oper_time)`、`idx_user_time(user_id, oper_time)`。`module` 不在任何索引前缀中 → 回表过滤。10 万行/年 × 5 年 = 50 万行，尚可接受，但**审计场景常按模块全量导出**（等保取证），届时全表扫描 + 回表 50 万次。建议改为 `(module, oper_time)`（替换 `idx_oper_time`，保持 2 个二级索引不超标）。同时 `request_params varchar(2000)` 在 utf8mb4 下最长 8000 字节，**批量导入的参数 JSON 必然被截断**（FR-106 导入 10 万条，若把文件路径+参数打包进 request_params 会超），应改 `text`。

## P1-6 `ai_model.is_current` 无唯一约束，可出现多条"当前生效版本"

### 问题
`ai_model`（L623-L637）：
- `uk_model_version(model_code, version)`、`idx_model_code(model_code)`；
- `is_current tinyint unsigned NOT NULL DEFAULT 0 COMMENT '1当前生效 0历史版本'`。

FR-604（L209）要求"模型版本可切换**可回滚**"。切换的实现通常是"`UPDATE ai_model SET is_current=0 WHERE model_code=?; UPDATE ai_model SET is_current=1 WHERE id=?`"。

### 后果
1. **两条 UPDATE 之间不是原子**（除非同事务，文档未要求）；并发切换或任务重试时会出现 **2 条 `is_current=1`**。而应用侧"取当前模型"的查询 `WHERE model_code=? AND is_current=1` 会报 `TooManyResultsException`（MyBatis `selectOne`）或随机取一条 → **预警判定用了错误的模型参数**（同一个 rule_code 用不同阈值），直接导致误报/漏报，且**极难排查**。
2. 无 `uk` 约束意味着数据库层**无法阻止**这种状态，只能在应用层靠纪律维持——违反"完整性由应用层保证"的前提是应用层**确实有保证**。
3. 无 `publish_time`/`publish_user_id`，FR-604 要求的"评估结果留痕""版本切换留痕"无处落库（与 P0-8 的模型参数历史表缺口同源）。

### 修复建议
```sql
-- 方案A（推荐，MySQL 8.0.13+ 支持函数索引与生成列）：
ALTER TABLE `ai_model`
  ADD COLUMN `current_flag` tinyint unsigned GENERATED ALWAYS AS
      (IF(`is_current` = 1, 1, NULL)) VIRTUAL COMMENT '生成列：仅当前版本为1，其余为NULL',
  ADD UNIQUE KEY `uk_current` (`model_code`, `current_flag`),
  ADD COLUMN `publish_time`    datetime DEFAULT NULL COMMENT '发布/生效时间' AFTER `is_current`,
  ADD COLUMN `publish_user_id` bigint unsigned DEFAULT NULL COMMENT '发布人' AFTER `publish_time`,
  ADD COLUMN `model_path`      varchar(500) DEFAULT NULL COMMENT '模型/参数文件路径（FR-604）' AFTER `params_json`;
-- 依据：唯一索引对多个 NULL 互不相等，因此同一 model_code 下"当前版本"至多 1 行
-- 切换模型必须走单条事务：UPDATE ai_model SET is_current = IF(id=?, 1, 0) WHERE model_code = ?;
```
```sql
-- 方案B（若不愿用生成列）：把"当前生效"抽到独立单行表
CREATE TABLE `ai_model_current` (
  `model_code` varchar(32) NOT NULL COMMENT '模型编码',
  `model_id`   bigint unsigned NOT NULL COMMENT '当前生效版本id',
  `update_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`model_code`)          -- 单行约束天然保证唯一
) COMMENT='模型当前生效版本（唯一性由PK保证）';
```
`idx_model_code(model_code)` 在方案 A 下变为**冗余索引**（`uk_current` 与 `uk_model_version` 的前缀已覆盖 `model_code`），应删除——这也顺带解决 P0-10 的索引名额问题。

## P1-7 角色未挂接测项 → 综合研判跨测项失效

### 问题
FR-303（L177）核心要求："**同一断面多测项/多指标联合研判**（如位移+应力+水压联动），输出综合风险分与建议级别"。

`mon_rule` 的适用范围字段（L377-L380）为：`hazard_type`、`item_type`（**单值**）、`stage`、`section_id`（单值）。ER 图（L55）只有 `MON_RULE ||--o{ WARN_EVENT`，**没有 RULE→ITEM 的多对多关系**。

### 后果
1. **组合规则无法表达"测项集合"**：`item_type` 是单个 `tinyint`，规则无法声明"同时涉及 101(围岩位移) 与 501(沉降量)"。
2. `section_id` 是单值，无法表达"某几个断面"或"全部断面"（只能靠 `0=全部` 约定，L380）。
3. 综合研判只能退化为"逐测项独立判定后按级别取最高"——**这正是需求文档 L42 点名的痛点**："现有预警多为单点阈值判断，缺乏趋势预测、突变检测与**多指标联动研判**"。也就是说，**当前数据库设计无法支撑本项目的核心卖点 FR-303**。
4. `warn_event.point_id` 注释为"组合规则事件为空"（L463）——这恰恰承认了组合事件**没有点位**，但同时又没有"组合事件包含哪些测项/点位"的关联表，导致事件详情页**无法展示参与判定的测项集合**（FR-306 要求"数据快照、判定依据留痕"）。

### 修复建议
新增 `mon_rule_item`（DDL 见 §P0-8.1 ⑫），并改造：
```sql
-- mon_rule：item_type 保留为"主测项"（用于触发），组合明细走 mon_rule_item
-- section_id 改造为多断面支持
ALTER TABLE `mon_rule`
  ADD COLUMN `section_scope` tinyint unsigned NOT NULL DEFAULT 0 COMMENT '0全部断面 1指定断面(见mon_rule_section)' AFTER `section_id`,
  ADD COLUMN `stage_scope`   tinyint unsigned NOT NULL DEFAULT 0 COMMENT '0全阶段 1指定阶段' AFTER `stage`;

-- warn_event：记录参与研判的测项集合与风险分（FR-303 输出）
ALTER TABLE `warn_event`
  ADD COLUMN `risk_score` decimal(5,2) DEFAULT NULL COMMENT '综合风险分（FR-303）' AFTER `warn_level`,
  ADD COLUMN `rule_item_json` varchar(2000) DEFAULT NULL COMMENT '参与判定的测项/权重/实测值集合' AFTER `trigger_value`,
  ADD COLUMN `judge_channel` tinyint unsigned NOT NULL DEFAULT 1 COMMENT '1快速通道(阈值) 2统计通道(速率/突变/趋势)' AFTER `rule_item_json`;
```
