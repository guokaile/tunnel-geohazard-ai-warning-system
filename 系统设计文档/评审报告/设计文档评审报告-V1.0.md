## 1. 🔴 阻断级问题（P0：必须先解决）

### P0-1 字典值溢出列类型：6 类监测对象中有 4 类无法建立点位

**位置**：`3.数据库设计说明书.md:357`（`mon_point.item_type`）、`:378`（`mon_rule.item_type`）、`:465`（`warn_event.item_type`）、`:674`（字典取值）、`:799`（附录A DDL）

**证据（已机械核验）**：

```sql
-- 表定义（3.6.3 L357 / 3.6.5 L378 / 3.6.5 L465 / 附录A L799 四处一致）
`item_type` tinyint unsigned NOT NULL COMMENT '测项'

-- 字典取值（3.7.1 L674），共 16 个值：
101=围岩位移  102=锚杆轴力  103=钢架应力
201=涌水量    202=水压      203=地下水位
301=CH4浓度   302=CO浓度    303=H2S浓度   304=风速
401=泥水流量  402=孔隙水压
501=沉降量    502=下沉速率
601=净空收敛  602=周边位移
```

**机械核验结果**：`tinyint unsigned` 取值范围 **0~255**，而 16 个字典值中 **10 个 > 255**（301/302/303/304/401/402/501/502/601/602）。在 MySQL 默认 `STRICT_TRANS_TABLES` 下写入报 **`ERROR 1264 (22003): Out of range value`**。

**受影响范围**（按字典首位数字对应 `hazard_type`）：

| hazard_type | 监测对象 | 测项取值 | 是否可用 |
|---|---|---|---|
| 1 | 坍塌 | 101/102/103 | ✅ 正常 |
| 2 | 涌水/突水 | 201/202/203 | ✅ 正常 |
| **3** | **瓦斯及有害气体** | **301/302/303/304** | ❌ **全部溢出** |
| **4** | **突泥** | **401/402** | ❌ **全部溢出** |
| **5** | **地表沉降/拱顶下沉** | **501/502** | ❌ **全部溢出** |
| **6** | **围岩收敛位移** | **601/602** | ❌ **全部溢出** |

**即 6 类监测对象中有 4 类（瓦斯、突泥、沉降、收敛位移）在严格模式下无法建立任何监测点位**，而瓦斯超限正是 `1.2.3 场景一` 的主场景。`FR-101`（数据接入）与 `G1`（覆盖 6 类监测对象）直接失败。非严格模式下则发生**静默截断**（301 → 45），点位测项被悄悄改写成另一个合法值——比报错更危险。

**理由**：这是"照文档建库就写不进数据"的一类缺陷，且**三张表、四处定义、附录 DDL 全部一致地错**，说明不是笔误而是设计疏漏。它也解释了为什么必须做**DDL 实跑验证**（见下方 P0-3），而不是纸面评审。

**改法**：
1. `mon_point.item_type`、`mon_rule.item_type`、`warn_event.item_type` **三处统一改为 `smallint unsigned`**（附录A DDL 同步）。
2. 把"字典值必须落在列类型取值范围内"加入 `3.11` 的**脚本自检项**（见 P0-3 的验证脚本）。
3. 顺带复核其余窄类型字段：`warn_level`(1~4)、`hazard_type`(1~6)、`quality`(0~3)、`source`(1~5)、`warn_status`(1~6) 均在 `tinyint` 范围内，**无需修改**——只有 `item_type` 一个字段有问题。

### P0-3 建库脚本从未实跑验证：DDL 从未执行过一次，且缺 `MAXVALUE` 兜底

**位置**：`3...md:765`（"其余 33 表阶段7按 3.6 规格生成"）、`:782-786`（附录A 分区 DDL）、`:750`（"全部脚本幂等"承诺）、`:118`（建分区任务）

**问题（三项叠加）**：

**(a) 全量 DDL 从未在真实 MySQL 上执行过。** 35 张表中只有 2 张给出完整 DDL，其余靠"按规格生成"。P0-1 的字典溢出、`data_point_latest` 违反必备字段规范、`sys_user` 缺 `fail_count`/`lock_time`（"连续 5 次锁定 30min"无处落库）都是纸面评审发现的问题——**实际执行一遍会暴露更多**。`0.待澄清问题清单` 的技术栈矩阵里 Spring Boot 一栏标的是"⏳ 待首次构建验证"，**DDL 连这样的标记都没有**。

**(b) 分区无 `MAXVALUE` 兜底，建分区任务失败 = 当月数据全量写入失败。** 附录A DDL 最后分区之后**没有 `pmax VALUES LESS THAN (MAXVALUE)`**：

```sql
PARTITION BY RANGE COLUMNS(`ts`) (
  PARTITION p202601 VALUES LESS THAN ('2026-02-01'),
  PARTITION p202602 VALUES LESS THAN ('2026-03-01')
  -- 无 MAXVALUE 兜底分区
);
```

建分区任务（`3...md:118`：应用内定时、每月 1 日 00:10、**失败无告警**——见 P1-15）一旦未执行（服务被停、磁盘满、DDL 锁等待、跨月时无人值守），次月起**每条写入都报 `ERROR 1526 (HY000): Table has no partition for value`**，静默累积到整月数据丢失，且月内无任何数据可查。

**(c) "全部脚本幂等"是空头承诺。** `3...md:750` 要求"全部脚本幂等（**IF NOT EXISTS** / 按 sys_schema_version 判断跳过）"，但 **MySQL 不支持 `ALTER TABLE ... ADD PARTITION IF NOT EXISTS`** —— 分区脚本无法用该机制实现幂等，必须改为"查 `information_schema.PARTITIONS` 后动态拼 SQL"。

**改法**：
1. **阶段7 开工前**用真实 MySQL 实例执行一遍全量 DDL，纳入 `T9` 验收标准：*"35 张表全部创建成功，无 error、无 warning"*；并补一条**字典值范围自检**（见下表）。
2. 分区表**必须增加 `pmax VALUES LESS THAN (MAXVALUE)` 兜底分区**（官方手册确认 RANGE COLUMNS 支持 MAXVALUE 且必须置于最后），杜绝"无分区可写"。
3. 把"建分区任务失败告警 + 每月分区存在性校验"纳入 `2.9` 与 `P1-15` 的自监控需求。
4. 分区脚本改为 **`information_schema` 驱动**的幂等实现，并修正 `3...md:750` 的表述。

**可直接执行的 DDL 静态校验 SQL（建议作为评审附件留档）**：

```sql
-- ① 唯一键是否遗漏分区键（MySQL 分区硬约束）
SELECT t.TABLE_NAME, t.INDEX_NAME, t.COLUMN_NAME
FROM information_schema.STATISTICS t
JOIN information_schema.PARTITIONS p
  ON p.TABLE_NAME = t.TABLE_NAME AND p.PARTITION_NAME IS NOT NULL
WHERE t.NON_UNIQUE = 0 AND t.TABLE_SCHEMA = DATABASE()
  AND t.COLUMN_NAME NOT IN (
    SELECT PARTITION_EXPRESSION FROM information_schema.PARTITIONS
    WHERE TABLE_NAME = t.TABLE_NAME AND TABLE_SCHEMA = DATABASE())
GROUP BY t.TABLE_NAME, t.INDEX_NAME;

-- ② 字典值是否溢出目标列类型（本项即可捕获 P0-1）
SELECT d.dict_code, i.item_value, c.COLUMN_TYPE, c.TABLE_NAME, c.COLUMN_NAME
FROM sys_dict_item i
JOIN sys_dict_type d ON d.id = i.dict_type_id
JOIN information_schema.COLUMNS c
  ON c.TABLE_SCHEMA = DATABASE() AND c.COLUMN_NAME = d.dict_code
WHERE c.DATA_TYPE IN ('tinyint','smallint')
  AND CAST(i.item_value AS UNSIGNED) > CASE c.DATA_TYPE
        WHEN 'tinyint' THEN IF(c.COLUMN_TYPE LIKE '%unsigned%', 255, 127)
        ELSE IF(c.COLUMN_TYPE LIKE '%unsigned%', 65535, 32767) END;
```

### P0-4 核心指标：验收用例自己证伪了自己的容量承诺

**位置**：
- `1.需求规格说明书.md:155`（FR-101 验收要点）*"模拟网关推送 1000 点、30s 周期连续 24h，数据零丢失"*
- `1.需求规格说明书.md:247`（NFR-P2）*"日入库 ≥100 万条；峰值 ≥3000 条/min 不积压"*
- `3.数据库设计说明书.md:759`（容量上限行）*"上限（5000 点×30s 全开）1440 万/天 → 原始表 1 年 ≈736GB"*

**问题**：三处数字互相矛盾，且**验收用例本身就超标**。

| 口径 | 计算 | 结果 |
|---|---|---|
| FR-101 验收场景 | 1000 点 ÷ 30s × 86400s | **288 万条/天** |
| NFR-P2 承诺 | — | 100 万条/天（峰值 3000 条/min = 432 万条/天） |
| 平均速率承诺 | 100 万 ÷ 86400 | 11.6 条/s |
| 峰值承诺 | 3000 ÷ 60 | **50 条/s** |
| FR-101 实际产生 | — | **33.3 条/s 持续 24h** |

**结论**：FR-101 的验收用例要求系统**连续 24 小时稳定处理 33.3 条/s**，已经达到文档自称"峰值 50 条/s"的 67%，而这是**常态而非峰值**。如果按 NFR-P2 的均值口径（11.6 条/s）配置容量，FR-101 必挂。

更严重的是 `1.8.2` 假设 *"点位 1000~5000"*，而 `2.10.1` / `3.12` 的容量模型全部建立在"日 100 万条"上。**5000 点按需求文档允许的最快频率（30s）全开 = 1440 万条/天**，是设计基线的 **14.4 倍**。文档自己在 3.12 承认了这个缺口却没有收敛它。

**理由**：这是**需求→架构→验收三者未闭环**的典型病症。大厂评审在此处会直接打回：一个安全监测系统的容量承诺，不能同时存在 14 倍自相矛盾的两个口径。

**改法**：
1. **定义唯一权威容量口径**，建议：*"设计基线 = 3000 点 × 60s 周期 + 2000 点 × 300s 周期 ≈ 490 万条/天，持续写入 ≥100 条/s，峰值 ≥300 条/s"*，然后让 FR-101 验收用例、NFR-P2、架构 2.10、数据库 3.12 **全部引用同一组数字**。
2. FR-101 验收用例改为引用该基线，并补充**明确的前置条件**（哪些点位、什么频率、持续多久、判定"零丢失"的具体方法）。
3. NFR-P2 的"峰值 3000 条/min"必须注明**瞬时峰值持续时间**（如"持续 ≥10 分钟"），否则"峰值"没有工程意义。

**问题**：这是 **2026-09 启动的新项目**，却锁定了一个 **2026-04 已完全 EOL、不会再有安全补丁** 的数据库版本。文档给出的理由是"需求指定"，并把风险等级定为"**低**"、应对措施是"一期锁定 8.0.46 开发"。

**理由**：
1. **等保二级明确要求"漏洞管理"与"入侵防范"**。使用无补丁的数据库，测评时属于**高风险整改项**，可能直接导致测评不通过。
2. **架构风险矩阵的定级错误**：R8 影响写"长期运维安全补丁风险"，可能性写"低"，等级写"低"。正确评估是：*影响=高（合规不通过），可能性=高（确定会发生）*，即**高风险**。把"确定发生的合规风险"评为"低"，是风险矩阵方法本身的失效。
3. `2.13` R-A3 的应对是"T9 同步验证 8.4 LTS 初始化兼容性"——**把版本升级当成可选项（verify），而不是当作必办项（commit）**。对一个全新项目，正确做法是**直接起在受支持版本上**，而不是"先用 EOL 版本开发，以后再迁"。

**改法**：
1. 将数据库版本改为 **MySQL 8.4.x LTS**（保守、与 8.0 兼容度最高）或 **9.7.x LTS**（生命周期最长），**并把该决定写进 `0.待澄清问题清单` 的决策记录**。
2. 若甲方合同确实写死 8.0.46，则：① 在 `1.7.3 外部依赖` 与 `1.8.1 风险清单` 中把 R8 升级为**高影响/高可能性**；② 增加"甲方确认接受 EOL 版本"的**书面签字项**；③ 在验收前置条件中加入"8.4 LTS 升级验证通过"。
3. 复核 JDBC 驱动版本与目标服务端版本匹配（`mysql-connector-j 9.x` 连接 8.4 需验证）。

### P0-8 密钥管理方案缺失，导致"加密"存储形同虚设

**位置**：`3.数据库设计说明书.md:224`（`sys_config.config_value` "密钥类存占位/密文"）、`:280`（`sys_third_app.app_secret` "签名密钥（密文存储）"）、`:730`（备份 AES 加密，密钥 `${BACKUP_KEY}`）、`2.系统架构设计说明书.md:452`（"`${BACKUP_KEY}` 初始化脚本生成"）

**问题**：文档三处要求"密文存储/加密"，但**没有任何一处说明**：
1. 用什么算法、什么密钥；
2. **密钥存在哪里**（这是关键——若密钥明文写在 `application.yml`，则"加密存储"只是障眼法）；
3. 密钥如何轮换、如何备份、灾难恢复时如何取回；
4. 应用以什么身份解密（配置中心？环境变量？密钥文件权限？）。

**理由**：这是**安全设计的根本性缺口**。等保二级"数据保密性"条款要求的是**有效**的加密，而不是"字段名叫密文"。更实际的后果：**备份加密密钥丢失 = 所有备份永久不可恢复**，与 `NFR-R1`（99.5% 可用性）和 `RPO≤24h` 直接冲突。文档却要求"每日备份 + 保留 3 代 + 每周 1 代"，**密钥一丢，4 代备份全废**。

**改法**：
1. 新增《密钥与凭据管理设计》章节，明确：算法（建议 AES-256-GCM，带认证）、密钥来源、存放位置与文件权限（建议独立密钥文件 + Windows ACL 限制到服务账号，且**与备份文件物理分离存放**）、轮换周期、轮换操作步骤。
2. `sys_config` / `sys_third_app` 的密文列**改为 `varbinary` 或 base64 `varchar`**（当前 `varchar(64/128)` 存 AES-GCM 密文+IV+Tag 可能不足，需核算）。
3. **备份恢复演练必须包含"仅用备份文件 + 密钥分片/纸质记录恢复"的完整演练**，并写进 `3.10` 的"恢复演练"验收标准。文档现已写"每季度演练一次"，但未定义**演练失败的处置流程**。
4. 在 `2.12.3` 安装流程中增加"密钥生成与安全交付"步骤，并明确**初始密钥不由安装脚本硬编码**。

## 2. 🟠 严重级问题（P1：现场事故或验收失败）

### P1-1 错误码体系与统一响应体自相矛盾

- `2.3.4`（`:186`）：*"成功 code=**00000**"*，错误码 5 位数字。
- `系统架构设计.md:214-220`：统一响应示例 `{"code": 200, ...}`。

**问题**：`00000` 是 5 位字符串，`200` 是 3 位数字。二者不可能同时成立。而 `3.6.1` 中 `sys_oper_log.response_code` 定义为 `varchar(8)`，说明实现者已经察觉"可能有前导零"，但文档未统一。**若 `code` 声明为 JSON number，`00000` 会被序列化为 `0`，前导零静默丢失**，前端判断全部失效。

**改法**：统一为**字符串型 5 位错误码**，并在接口规范中明确 `code` 为 `string`；同步修正 `系统架构设计.md` 的示例，并输出**全量错误码清单**（当前只有命名规则，没有清单，见 P0-7）。

### P1-3 实时刷新与缓存 TTL 数值耦合，导致缓存完全失效

- `2.5`（`:229`）：看板**轮询 5s**。
- `2.10.2`（`:353`）：Caffeine 最新值 **TTL 5s**。

**问题**：TTL == 轮询周期，意味着**每一个请求都恰好错过缓存**（缓存写入后 5s 过期，客户端恰好 5s 后来取）。这是典型的缓存参数拍脑袋问题。

**改法**：TTL 应显著大于轮询周期（如 TTL 10~15s + 数据写入时主动刷新），或改为**写入驱动更新**：数据入库时同步更新 Caffeine 中的最新值，看板读缓存基本 100% 命中。后者更符合 `2.4.1` 已经设计的"点位最新值表"思路。

### P1-4 表达式引擎的安全沙箱未设计（RCE 风险）

**位置**：`2.2.3` 选型 Aviator 5.4.x，`3.6.3` `mon_rule.expression_json` 存储 Aviator 表达式

**事实**：AviatorScript 存在 **CVE-2021-41862（CVSS 9.8 CRITICAL）**——"通过 BCEL 编码的表达式允许代码执行"，影响 5.2.7 及以下。来源：[GitLab Advisory Database](https://advisories.gitlab.com/pkg/maven/com.googlecode.aviator/aviator/)

**问题**：即使使用已修补的 5.4.x，**"允许用户通过界面配置任意表达式"本身就是一个代码执行面**。文档中：
- `2.8` 安全架构完全没有提及表达式引擎的沙箱/白名单；
- 没有定义**谁能配置规则**（`1.3.2` 权限矩阵中"规则/模型参数"给了技术专家）；
- 没有定义表达式的**语法白名单**（允许哪些函数、禁止哪些调用）。

**理由**：技术专家账号一旦被冒用（或内部人员误操作），即可通过规则表达式在服务器上执行任意代码。对一个接了现场工业网络的系统，这是**最高危的攻击面**。

**改法**：
1. 在 `2.8` 增加"表达式引擎安全"条目：**禁用 AviatorScript 的模块加载/Java 反射能力**，只暴露白名单变量（`value`、`rate`、`windowAvg`…）与白名单函数（`abs/min/max`），**禁止 `use`/`import`/类名调用**。
2. 规则保存时做**AST 静态校验**（拒绝非白名单节点），而不是运行时兜底。
3. 规则表达式**不落库原始脚本即执行**，需经"提交→校验→人工复核→启用"流程（这也正好对应 `FR-301` 要求的"变更全留痕"）。
4. 把该风险写入 `2.13` 风险表，并把"表达式沙箱验证"加进 T1~T10 前置验证任务。

### P1-5 内存队列无法"落盘"，与"数据零丢失"承诺冲突

**位置**：`2.9`（`:328`）*"应用内队列数据落盘策略（阶段6定稿：队列满/关机时快照落盘）"*

**问题**：`2.4.1` 选的 Disruptor 是**纯内存环形队列（RingBuffer）**。它的**设计前提就是无持久化**——"队列满/关机时快照落盘"在 Disruptor 语义下**不可实现**（RingBuffer 是复用槽位，已被覆盖的数据无法恢复）。文档把"落盘"这一不可能完成的动作推给了阶段6。

同时 `2.4.1` 的背压策略是 *"接近容量阈值时降级（**丢弃旧数据**并记数告警）"*——**直接与 `FR-101` 验收要点"数据零丢失"矛盾**。

**理由**：对地质灾害预警系统，"丢数据"的后果是**漏报**（该报警时没报），这是最严重的失效模式。文档在架构层面主动引入了丢数据机制，却没有定义丢失的判定标准、告警级别和补数流程。

**改法**：
1. 明确区分两条路径：
   - **快通道（可容忍极端情况降级）**：内存队列用于实时判定；
   - **可靠通道（不允许丢）**：接入层解析后**先写本地 WAL/磁盘队列**（如 Chronicle Queue、RocksDB、或最简单的"按日期分文件的追加写"），再由消费者读取入库。这才是"零丢失"的正确实现。
2. 若坚持纯内存队列，则必须把 `FR-101` 的验收要点从"数据零丢失"改为可度量的**"数据完整率 ≥99.99%"**，并定义**丢失量的计算方法与告警阈值**，同时写入 `1.8.1` 风险清单。
3. 无论选哪种，**"队列满"必须是一个可观测事件**（指标 + 告警），当前文档只有"记数告警"四个字，无指标定义。

### P1-6 备份保留策略在四份文档中三种口径

| 位置 | 口径 |
|---|---|
| `2.7.3`（`:291`） | backup 目录"**保留 3 代滚动**" |
| `2.9`（`:329`） | "保留 **3 代滚动 + 每周异地介质建议**" |
| `3.10`（`:732`） | "滚动保留最近 **3 代 + 每周 1 代（共 4 代）**" |

同时 `3.12` 容量模型的"业务表+备份 ≈40GB"**未说明按几代备份计算**。按 `data_sample` 1 年 ≈51GB 推算，**单份全量备份就超过 51GB**，4 代 = 200GB+，**已超过"业务表+备份 40GB"的估算，也逼近 500GB 磁盘规格的一半**。

**改法**：统一为"**每日全量保留 N 代 + 每周全量保留 M 代**"，明确 N/M 的具体数值；备份容量按 `单份备份大小 × (N+M) × 压缩比` 重新核算并回写 `3.12`；同时纳入 binlog（见 P1-7）。

### P1-7 未评估 binlog 占用与 PITR 能力

**位置**：`3.10`、`3.12` 全文无 binlog 相关内容

**问题**：
1. `3.12` 的磁盘估算**遗漏 binlog / relay log / undo / redo / 临时表空间**。按日 100 万条写入估算，binlog 日增量可观，且默认 `binlog_expire_logs_seconds` 为 30 天，占用可能达数十 GB。
2. 只做"每日全量备份"意味着 **RPO 最坏 = 24h**（文档 `3.10` 已承认）。对一个预警系统，**丢失 24 小时的监测数据**是否可接受？文档未做论证。
3. **没有 PITR（时间点恢复）能力**，误删数据只能恢复到前一天 02:00。

**改法**：
1. `3.12` 补充 binlog 容量项与保留天数（建议 7 天），并复核 500GB 是否仍然够用。
2. 明确 RPO 论证：若 24h 不可接受，需开启 binlog + 每日全量，将 RPO 降至分钟级，并写明恢复步骤与**演练通过标准**。
3. `NFR-R1`（99.5%）与 RPO/RTO 应放在同一张可靠性指标表中，当前 `3.10` 的 RPO/RTO 与 `1.5.3` 的 NFR-R 编号体系**互不引用**。

### P1-8 权限矩阵与角色定义不一致，且消警职责未定义

**位置**：`1.3.1` 角色职责 vs `1.3.2` 权限矩阵

| 缺口 | 说明 |
|---|---|
| 技术专家 | 矩阵写"预警确认/派单 = √（复核）"，但 `1.3.1` 职责是"预警复核、参数定稿"，未提"派单" |
| 管理领导 | 矩阵写"督办"，但"督办"**未定义任何系统动作**（是看板标记？催办消息？） |
| **消警权限** | `FR-404` 要求"技术专家/值班调度复核消警"，但矩阵中**完全没有"消警"这一行** |
| **误报登记** | `FR-401` 有该动作，矩阵中无对应权限点 |
| 复核独立性 | 未定义"确认人 ≠ 消警人"（职责分离），存在**自确认自消警**绕过闭环的风险 |

**改法**：矩阵补齐所有**系统动作级**权限点（确认/派单/反馈/复核/消警/误报登记/规则变更/参数变更/数据导出），并增加"**职责分离约束**"一列，明确哪些动作不能由同一人连续完成。

### P1-9 AI 能力指标不可验证，且与"不允许漏报"的安全目标冲突

| 问题 | 位置 | 说明 |
|---|---|---|
| 指标含义不明 | `FR-601`（`:206`）"预测方向正确率 ≥80%" | 未定义**基线**（对比"随机猜"还是"预测值不变"？），未定义评价样本与统计方法 |
| **无漏报率指标** | `FR-603`（`:208`）只要求"输出三项指标" | **对地质灾害预警系统，漏报（FN）才是致命失效模式**，而全文只把准确率/漏报率当作"报告里的数字"，从未设定阈值 |
| 验收不可执行 | `FR-602`（`:207`）"注入已知突变样本**全部检出**" | 未定义样本数量、类型、信噪比、注入方式；"全部检出"在统计上不可验收 |
| 无冷启动方案 | `R4`（`:421`）承认"无带标签历史数据" | 却没有定义**上线初期如何验证模型有效**（影子运行？专家标注样本？分阶段放开？） |
| 无影子期 | 全文 | 模型直接决定预警级别并触发短信/声光/撤人，**没有"只记录不生效"的影子运行期** |

**理由**：安全类系统上线的通行做法是"**先影子、后生效**"。当前设计让未经验证的统计模型**第一天就驱动撤人指令**，一旦误报频繁，现场会失去信任（`R1` 已预判此风险，但应对只是"参数化配置"）。

**改法**：
1. 建立**预警能力指标体系**：漏报率（FN Rate）上限、误报率（FP Rate）上限、平均提前预警时间（Lead Time）、判定延迟 P95。**漏报率必须是带阈值的硬指标**。
2. 模型验收改为**基于固定标注样本集**的离线评估（样本集随文档交付，可复现），而不是"上线后评估"。
3. 增加**模型影子运行期**：≥30 天只记录判定结果不触发通知，与人工判断比对，达标后再切换为生效模式。
4. `2.11` 已设计"模型版本可切换（FR-604）"，需补充**回滚触发条件**（如"连续 N 次误报自动回退上一版本"）。

### P1-10 预警风暴抑制/去重机制完全缺失

**位置**：`M3 预警中心` 全文；`3.6.5` `warn_event` 表

**问题**：没有任何机制防止以下场景：
- 一个断面 10 个测点同时超限 → **瞬间生成 10 条橙级预警** → 10 条短信 + 10 次声光；
- 持续超限期间数据每分钟上送一次 → **每分钟重复生成同一条预警**；
- 组合规则与单点规则同时命中同一事件。

`warn_event` 表**没有去重键**（如 `point_id + rule_id + 时间窗` 唯一约束），也没有"事件合并/抑制"字段。

**理由**：告警风暴是本类系统的**头号工程问题**。后果：短信费用失控、现场对报警麻木（"狼来了"）、真实预警被淹没——这直接摧毁 `G2/G4` 的业务价值。

**改法**：
1. 引入**去重与抑制模型**：`(point_id, rule_id)` 在**活跃期内不重复产生事件**，重复命中仅更新 `snapshot_json` 与命中次数；
2. 引入**事件聚合**：同一断面同一时间窗内多测点命中，聚合为**一个事件 + 多触发依据**（`warn_event_detail` 子表）；
3. 引入**静默期/抑制规则**：已确认处置中的事件在 N 分钟内不再重复通知；
4. 通知侧增加**频次限制**（单通道单位时间最大发送量）与**升级去重**（升级通知只发增量对象）。
5. 相应调整 `3.6.5` 表结构并补充章节说明。

### P1-11 防重放机制与离线补传业务直接冲突

| 设计 | 位置 | 要求 |
|---|---|---|
| 防重放 | `2.6.1`（`:243`） | "请求携带时间戳+nonce，**超时窗口（5min）内**拒绝重复请求" |
| 离线补传 | `FR-104`/`FR-503` | 断网填报，**联网后补传**（断网时长未知，可能数小时） |

**问题**：两个设计**在协议层互斥**。移动端断网 2 小时后补传，请求时间戳必然超过 5 分钟窗口，会被防重放机制**直接拒绝**。文档两处都写了，但**没有一处指出这个冲突**。

同时 `2.6.1` 要求"写操作携带幂等键"，但**没有定义幂等键的生成规则与存储位置**（服务端存哪里？本地 Caffeine 存 5 分钟？重启后失效？）。

**改法**：
1. 明确**防重放的适用范围**：仅适用于**在线实时接口**（登录、写配置、下发指令）；**数据补传类接口走独立的批量通道**，以"批次号 + 幂等键"保证幂等，不施加 5 分钟时间窗。
2. 定义幂等键生成规则（客户端 UUID）与服务端存储（建议落库 `idempotent_record` 表 + 唯一索引，保留 ≥24h）。
3. 明确定义**补传的最大回溯窗口**（如 7 天）与超窗数据的处理方式（拒绝/标记）。

### P1-12 采集链路时钟同步问题未处理

**位置**：`3.6.4` `data_sample.ts`（采样时间，来自报文）、`receive_time`（入库时间）

**问题**：`ts` 直接采信网关上报的时间戳，但**全文没有定义**：
- 网关与服务器的**时钟同步要求**（NTP？允许偏差多少？）；
- 若网关时钟漂移/错误（如年份写成 2020），系统如何处理（拒绝入库？按 `receive_time` 纠正？标记质量位？）；
- 时钟回拨对**速率计算、突变检测、滑动窗口**的破坏。

**理由**：这是工业数据采集的经典陷阱。**时间戳错误 = 趋势计算全错 = 预警失效**，而且这类错误往往在运行数月后才被发现，届时数据已不可信。文档 `FR-102` 的校验只覆盖"范围/跳变/重复/缺失"，**没有时间维度的校验**。

**改法**：
1. `FR-102` 增加**时间校验**：与 `receive_time` 偏差超过阈值（建议 ±5min）的数据标记为新质量位（如 `4=时间异常`）；
2. `2.9` 增加"**时钟同步**"条目：要求现场网关与服务器启用 NTP，并在系统内提供"网关时间偏差监控"页面/告警；
3. `3.7.1` 的 `quality` 字典增加时间异常枚举值。

### P1-13 移动端离线场景未定义实现方案，验收用例"无法执行"

**位置**：`FR-104`/`FR-503` 验收要点、`场景三`（`:98`）

**问题**：文档多处要求"移动 H5 离线暂存、联网补传、拍照上传"，但：
- **隧道内无网络是常态**（这正是本系统的业务前提），H5 的离线能力依赖 Service Worker + IndexedDB，**方案未提及**；
- **照片离线暂存的容量与策略未定义**（一张照片 2~5MB，IndexedDB 在移动浏览器有配额限制）；
- **验收用例写的是"断网填报 10 条记录，恢复网络后全部补传成功"**——但**没有定义"断网"的模拟环境**（关闭 WiFi？隧道内实测？），**没有限定附件大小与数量**，验收时无法判定通过与否。

**改法**：
1. 新增《移动端离线方案设计》：Service Worker 缓存策略、IndexedDB 数据结构、**附件压缩与分片上传**、冲突解决（离线期间数据被他人修改）、补传失败的可见与人工重试入口。
2. 验收用例量化：*"在飞行模式下连续填报 20 条记录（含 3 张 2MB 照片），恢复网络后 5 分钟内全部上传成功且无重复"*。
3. 明确**H5 离线能力的浏览器基线**（`NFR-C2` 只写 Chrome/Edge 90+，移动端未限定）。

### P1-14 规则变更留痕在数据库中无落地表

**位置**：`FR-301`（`:175`）*"规则版本化、启停、生效时间，**变更全留痕**"*；`3.6.3` `mon_rule` 表只有 `version` 字段

**问题**：`mon_rule` 表**通过更新 `version` 字段实现"版本化"，属于原地覆盖**——旧版本的表达式内容**不会被保留**，无法回滚、无法追溯"某次误报当时用的是哪版规则"。这与 `FR-301` 的"变更全留痕"和 `FR-604`（模型"可切换可回滚"）**均不满足**。

**改法**：增加 `mon_rule_history` 表（规则 id、版本号、`expression_json` 快照、操作人、操作时间、变更说明、生效/失效时间），或改为"**规则表只追加不更新**，以 `(rule_code, version)` 为主键，`effective_time` 决定当前生效版本"。后者与 `3.6.3` 已有的 `effective_time`/`expire_time` 字段更契合。

### P1-15 系统自身健康与采集链路监测缺失（"沉默失效"风险）

**位置**：`M7 基础支撑`、"运维"相关章节全文

**问题**：一个 7×24 安全监测系统，**没有任何要求来监测"系统自己是否还在正常工作"**：
- 采集网关掉线、数据停止上送 → **没有"数据中断告警"要求**（`FR-201` 只在看板上"显示"离线状态，无人看就不会发现；`mon_point.last_data_time` 字段存在但无配套任务）；
- 数据队列积压、消费线程死亡 → 无监测；
- 通知通道（短信/声光）失效 → `FR-703` 只有"通道健康检测"配置项，**没有"通道失效时如何兜底/如何告警"**；
- 磁盘水位（`2.9` 有 ≤85% 告警）、JVM 内存、MySQL 连接池 → 只有阈值，**无采集手段**；
- 定时任务（分区创建、聚合、清理、备份）**执行失败无告警**。

**理由**：安全系统的**最严重失效模式是"沉默失效"**——系统看起来在运行，实际已经不预警了。`NFR-R3` 只保证了"进程活着"（Windows 服务自动拉起），**不保证"业务活着"**。`FR-802` 的"设备在线率"是给领导看的展示指标，不是**主动告警**。

**改法**：
1. 新增 `M10 系统自监控` 需求域（P0），至少包含：
   - **采集链路监测**：点位无数据超时（按 `collect_freq_sec × N`）→ 生成"数据中断"事件并通知；
   - **任务执行监测**：分区创建/聚合/备份/清理任务失败 → 告警；
   - **资源监测**：磁盘、内存、连接池、队列深度 → 超阈值告警；
   - **通道监测**：短信/声光通道连续失败 N 次 → 告警并提示切换；
   - **心跳自检**：每日向值班人发送"系统运行正常"摘要（让"沉默"本身成为可感知信号）。
2. 数据库补充相应的**任务执行记录表**（`sys_job_log`）与**采集链路状态表**（或在 `mon_point` 基础上扩展）。
3. `2.5` 前端增加"系统健康"页面。

### P1-16 需求追溯矩阵倒挂（自上而下，无法自下而上追溯）

**位置**：`2.3.3` 模块与需求追溯矩阵

**问题**：矩阵的粒度是 **"模块 ↔ FR 编号列表"**（如 `tgaws-business` 一行塞了 30+ 个 FR）。它只能回答"这个模块做什么"，**无法回答"每个 FR 落在哪个模块/哪张表/哪个接口/哪条测试用例"**。同理，`3.4` 表清单也没有与 FR 的映射。

**理由**：大厂标准要求 **双向可追溯**：`需求 → 设计 → 表/接口 → 用例 → 验收`。当前只有"需求→模块"这一个粗粒度方向，导致：需求遗漏无法发现（评审时只能靠人肉比对）、变更影响面无法评估、测试覆盖无法证明。

**改法**：产出一张**需求追溯矩阵表**（建议直接放阶段4文档），列为：`FR 编号 | 需求名 | 实现模块 | 相关表 | 相关接口 | 相关页面 | 测试用例编号 | 验收要点 | 状态`。这张表是阶段4→阶段8 的主线索引，**投入产出比极高**。

> **§3D 汇总数据库专项审计（含 MySQL 官方手册约束核验与 InnoDB 行格式精算）的阻断级发现。**

### D-1（P0）`DROP PARTITION` 无边界算法，存在删除当月数据的实现路径

**位置**：`3...md:119`、`:721-722`（"超期月份 `DROP PARTITION`"）

**问题**：文档只说"超期月份删分区"，**没有给出判定算法**。而 `RANGE COLUMNS` 的语义是**上界**：`p202601 VALUES LESS THAN ('2026-02-01')` 装的是 **2026 年 1 月整月**数据，但分区名读起来像"2026 年 1 月 1 日"。两种最常见的实现都会出错：
- 按**分区名**解析"超期"→ 多删一个月（删掉本应保留的边界月）；
- 按"**上界所属月**"比较 → 在边界月会删掉**当月分区**。

而 `DROP PARTITION` 是 DDL 操作，**不产生 undo、无法通过 binlog 回滚**（叠加 P0-6 无 binlog 归档即**永久不可恢复**），且文档中**没有归档留痕表**记录"删了哪个分区、何时删的"（审计缺口）。

**改法**：改为**上界驱动 + 三重断言**，并新增 `data_archive_log` 留痕表：

```sql
-- 上界驱动：仅选中上界 <= 当前月首日 - 保留期 的分区，且永远排除当月
SELECT PARTITION_NAME, PARTITION_DESCRIPTION
FROM information_schema.PARTITIONS
WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'data_sample'
  AND PARTITION_NAME <> 'pmax'
  AND STR_TO_DATE(PARTITION_DESCRIPTION, '%Y-%m-%d %H:%i:%s') 
      <= DATE_SUB(DATE_FORMAT(CURDATE(), '%Y-%m-01'), INTERVAL 12 MONTH);
-- 删前三重断言：① 非 pmax ② 上界严格早于"当前月-保留期" ③ 归档任务已成功（开关开启时）
```

### D-2（P0）DBA 专项审计的其余 3 项阻断级发现（摘要）

> 完整证据、可执行 SQL 与改写 DDL 见配套文件：**《3.数据库设计说明书.审计报告.md》**（1573 行，含 DDL 校验 SQL、性能验证 SQL、分区生命周期演练、恢复演练验收标准）。

| 编号 | 问题 | 后果 |
|---|---|---|
| **DB-P0-a** | **秒级 `datetime` + 无去重键 = 丢数与重复二选一**。`data_sample.ts datetime` 为秒级，且**无任何唯一键**；`FR-101` 要求"断点续传/重连补传"，补传必然产生同秒多条 | 不加唯一键 → 重复样本污染 `sample_count`/`avg_value`，`FR-801` 完整率不可信；加 `(point_id,ts)` 唯一键 + `INSERT IGNORE` → **真实同秒第二条被静默吞掉**，违反 `FR-101`"数据零丢失"。量化：速率计算 Δt 量化误差 ±1s（30s 窗口 **3.3%**），两路时钟漂移 30s 时误差 **100%**。另 `quality=3 缺失` 无法表达（`value` 为 `NOT NULL`，而涌水量 0、CH₄ 本底 0 都是**真实零值**）。**改法**：`datetime(3)` + `sample_seq`；冲突走 `ON DUPLICATE KEY UPDATE` 并按 affected rows 判定重复、写 `data_dedup_log` 留痕，**禁止静默 IGNORE**；`value` 改可空 |
| **DB-P0-b** | **`FR-303`「多测项联动研判」在数据库层无法支撑**。`mon_rule.item_type` 是**单值**，ER 图**无 RULE→ITEM 多对多关系**，无法表达"位移+应力+水压联动" | 综合研判只能退化为"逐测项取最高级别"，**正是 `1...md:42` 点名的痛点**（"现有预警多为单点阈值判断，缺乏多指标联动研判"）。P0 需求 `FR-303` 实际无法实现。**改法**：增 `mon_rule_item`(rule_id, item_type) 关联表，并明确组合规则的表达式语义 |
| **DB-P0-c** | **`FR-801`/`FR-802` 的指标无任何落库表**，全部实时聚合。量化：单月数据完整率需扫 **4320 万行** GROUP BY（预估 30~180s） | 而 `FR-802` 要求"指标刷新 **≤1min**"——**架构上不可能**。**改法**：增 `rpt_stat_daily` 预聚合表，报表/驾驶舱只读预聚合结果；这同时也是 `2.5`"看板 ≤5s 刷新"的前提 |

**`is_deleted` + 唯一键的补充危害（升级 P2-3）**：除"编码不可复用"外，更危险的是**静默错行**——若应用查询漏过滤 `is_deleted`（最常见疏漏），接入按 `point_code` 会命中**已删除行**，数据挂到废弃 `point_id`，**看板不显示、预警不触发，而"入库成功"**；登录侧则可**用已注销账号登录**（等保二级身份鉴别不通过）。**改法**：`deleted_at datetime NULL` + `uk(code, deleted_at)`（MySQL 唯一索引视多个 NULL 互不相等，可容纳 1 个活跃行 + 多个历史删除行）。注意 `(code, is_deleted)` 是**不完整方案**（只允许删一次）。

**`ai_model.is_current` 只标记不约束（新增 P1）**：可出现**多条"当前生效版本"**，实现侧 `selectOne` 会抛异常或随机取——**预警可能用错阈值**。**改法**：加**函数唯一索引**或"部分唯一"约束（如 `is_current=1` 时 `uk_model_current(model_code, is_current)`，配合应用层事务保证），或改为 `ai_model_current` 指针表。

**审计日志"不可删改"零技术保障（新增 P1）**：`sys_oper_log`/`sys_login_log` 只是普通 InnoDB 表，应用账号必然有 `UPDATE`/`DELETE` 权，等保二级"安全审计"直接不符合。**改法**：三层——① `REVOKE UPDATE, DELETE`（含新增的时间线/级别日志/归档日志表）；② 哈希链（`prev_hash`/`row_hash`）；③ 归档留痕。

**聚簇键改造的时序性硬约束（新增 P1，决策层必须知道）**：分区表上 `ALTER TABLE ... DROP PRIMARY KEY, ADD PRIMARY KEY(point_id, ts)` 是**整表重建**，按基线 1.58 亿行/年需 **2~6 小时 + 1.6 倍磁盘余量**。**一旦试运行 30 天产生数据，改造窗口即不复存在** —— 与 P0-1 并列为本设计最紧要的两项决策，**必须在编码前定稿**。



### S-1（建议 P0）JVM + MySQL 内存分配 = 16G 的 100%，与 NFR-P5「内存 ≤70%」直接不相容

**证据**：
- `2...md:344`：*"内存分配 | 16G 总量：**JVM 4G + MySQL 缓冲池 8G + 系统 4G**"*
- `3...md:761`：*"MySQL `innodb_buffer_pool_size=8G`（占 16G 内存 **50%**）"*
- `1...md:250`（NFR-P5）：*"8C16G 单机：CPU 常态 ≤60%，**内存 ≤70%**"*

**问题**：4 + 8 + 4 = **16G = 100%**，而 NFR-P5 要求 ≤70%（即 ≤11.2G）。且"系统 4G"这一项**没有包含** MySQL 的 per-connection / sort / join buffer、Nginx、以及 Netty 的**堆外直接内存**（`2...md:116` 引入 Netty，DirectMemory 默认无上限，在 Windows 上会直接吃系统内存）。

**理由**：**NFR-P5 在现有分配方案下数学上不可能达标**。这不是"需要注意"，而是"这个非功能需求现在是假的"。验收时一旦实测内存占用，必然超 70%。

**改法**：把 `innodb_buffer_pool_size` 降至 **4~5G**（文档自述热数据仅为"近 3 天采样 + 全部业务表"，实测业务表总量不足 1G，4G 缓冲池已足够），并明确 JVM 参数：`-Xmx4g -Xms4g -XX:MaxDirectMemorySize=512m`；把 `2.10.1` 内存行改为"分配上限 + 预留余量，稳态目标 ≤70%"，并重新核算 `3...md:761` 的"占 50%"论证。

### S-2（建议 P0）目标库名不一致：文档 `tgaws` vs 代码 `mytest`

**证据**：`3...md:11` *"单库 `tgaws`"*、`:831` *"`${DB_NAME}` 固定 `tgaws`"*、`:740` *"建用户（最小权限：仅 tgaws 库）"* **对** `application.yml:6` `jdbc:mysql://localhost:3306/**mytest**`

**问题**：初始化脚本建 `tgaws` 库，应用连 `mytest` 库。现场安装后**要么启动即连接失败，要么连到一个不存在的库上跑起来**（取决于 MySQL 是否已存在 `mytest`）。这是"照文档施工必挂"的一类缺陷。

**改法**：连接串统一为 `${DB_HOST}:${DB_PORT}/${DB_NAME}`；在 `2.12.3` 安装向导第 6 步增加校验项"**连接串库名 == 初始化脚本库名**"，并把该字符串作为安装验证（第 8 步）的必过项。

### S-3 会话超时与令牌有效期互相矛盾，且 JWT 无服务端登出能力

**证据**：`2...md:315` *"会话 **30min** 超时"* **对** `:241` *"access token 有效期 **2h** + refresh 续签"*；`:321` *"剩余信息保护：**登出/超时清理会话**"*；`3` 的 35 张表中**无令牌/会话表**（`sys_login_log` 只是日志）

**问题**：① 会话 30min 超时而令牌 2h，两者取严则令牌形同虚设、取宽则 NFR-S2"会话超时自动退出"不成立——**文档没有说明以哪个为准**；② 无状态 JWT **无法在服务端"清理会话"**，登出后旧令牌在有效期内仍然可用，这与等保二级的"剩余信息保护"要求直接冲突。

**改法**：改为 **access token 30min + refresh token 2h（滑动续期）**；登出黑名单用 Caffeine 本地缓存实现（TTL = access token 剩余有效期），并在 `3` 中显式说明"因单机部署，登出黑名单使用应用内缓存而非令牌表"——**把"为什么没有令牌表"写清楚**，否则实现者会各写一套。

### S-4 规则匹配链路上缺少索引，判定链路会全表扫描

**证据**：
- `3...md:391`：`mon_rule` 的检索索引是 `idx_hazard_item_stage(hazard_type, item_type, stage)`
- `3...md:369`：`mon_point` 的索引是 `uk_point_code` / `idx_tunnel_section` / `idx_hazard(hazard_type)` / `idx_gateway`，**没有 `item_type` 索引**

**问题**：规则匹配的入口是"给定一个点位的 `hazard_type + item_type + stage` → 找出适用规则"。但**没有索引能高效回答"哪些点位属于某个 `item_type`"**（`data_sample` 只有 `point_id`，`mon_point.item_type` 无索引）。当需要"按测项批量判定/回算"时（补传数据到达、规则变更后重算、聚合统计），只能全表扫描 `mon_point` 或用 `idx_hazard` 后过滤。

**改法**：把 `idx_hazard(hazard_type)` 扩展为 **`idx_hazard_item(hazard_type, item_type)`**，保持索引总数不变（符合 `3.2` 的"单表 ≤5 索引"）。

### S-5（建议 P0）AI/统计模型的计算结果**没有任何结果表**，全部塞进 `varchar(4000)`

**证据**：
- `1...md:202-210`：M6 要求趋势预测（**含预测值与置信区间**）、突变检测、综合研判、模型评估、分析报告
- `3...md:623-637`：只有 `ai_model`（**模型注册表**），无结果表
- `3...md:480`：`warn_event.snapshot_json varchar(4000)` —— 预测值、置信区间、突变检出记录、多指标贡献**全部只能挤在这里**
- `3...md:654-665`：`rpt_report` 只有 `file_path`，**无结构化内容**，无法支撑 `FR-801` 报表统计

**问题**：这是**需求到数据模型的整块缺失**。`FR-601` 要求"输出未来时段预测值与置信区间"——**这些数据没有地方存**；预测曲线的展示（`FR-201` 实时曲线）也无数据来源。`FR-603` 要求模型可评估，评估样本的判定结果同样无处存放。

**理由**：`FR-601/602/603/605` 全是 **P0/P1 需求**，却在数据库设计中找不到落点。`varchar(4000)` 存结构化结果会导致：无法按条件查询、无法聚合统计、无法作为训练样本导出——**"数据沉淀为模型训练样本"（`1.6.1` 第 5 条）直接落空**。

**改法**：至少增加三张表：
- `ai_forecast`（`point_id`、`model_id`、`forecast_time`、`target_time`、`forecast_value`、`lower_bound`、`upper_bound`、`create_time`）；
- `ai_analysis_result`（`point_id`/`section_id`、`model_id`、`analysis_type`、`risk_score`、`result_json`、`window_start`、`window_end`）；
- `rpt_report_data`（`report_id`、指标编码、指标值、维度），或让 `rpt_report` 直接存结构化 JSON 而非仅 `file_path`。

**同时**：`warn_event` 增加 `risk_score decimal(5,2)`（`FR-303` 明确要求"输出**综合风险分**"，当前无字段存储，研判结果不可查、不可审计）。

### S-6（建议 P0）数据级权限在数据库层完全没有承载

**证据**：`2...md:316`：*"RBAC 最小权限；**菜单/按钮/数据三级权限**（监测员仅见本隧道数据）"* **对** `3...md:180`：`sys_permission.perm_type` 只有 `1菜单 2按钮` 两级；`sys_role` / `sys_user_role` **无 `data_scope` 字段**，也无"角色—隧道"授权表

**问题**：架构文档明确承诺的"数据级权限"在 35 张表中**没有任何字段或表承载**。这意味着"监测员仅见本隧道数据"这一**安全承诺无法实现**，实现者只能在 SQL 里硬编码过滤条件（违反 `2.1.2` 的"代码零硬编码"）。

**改法**：`sys_role` 增加 `data_scope`(tinyint：全部/本隧道/本断面/仅本人)；增加 `sys_role_tunnel`(role_id, tunnel_id) 承载多隧道授权；并在 `2.8` 访问控制条目中明确"数据级过滤在 `manager` 层统一注入，Mapper 不接受未经授权的查询条件"。

### S-7 四处 P0 验收要点要求的"留痕/版本化"没有对应的数据表

**证据**：

| 需求 | 要求 | 数据库现状 |
|---|---|---|
| `FR-103`（`:157`） | 点位"**参数变更留痕**" | `mon_point` 无变更历史表 |
| `FR-301`（`:175`） | 规则"**变更全留痕**"、"版本回滚" | `mon_rule` 靠**原地更新 `version` 字段**，旧版本内容不保留（见 P1-14） |
| `FR-502`（`:198`） | 巡检模板"**模板版本化**" | `patrol_template` 同样是原地 `version` 字段 |
| `FR-604`（`:209`） | 模型"评估结果留痕"、"可切换可回滚" | `ai_model` 用 `is_current` 标志，无变更历史 |

且 `sys_oper_log` 只有 `request_params`（`:239`），**没有 `before_value` / `after_value`**，无法从审计日志重建变更内容。

**问题**：四处 **P0/P1 验收要点**都要求"可回溯"，而数据模型只提供了"当前值"。**验收时无法演示"回滚到上一版本"**。

**改法**：统一策略——对规则/模板/模型/点位参数，采用"**版本表 + 当前生效指针**"或"**只追加不更新 + `effective_time` 决定生效版本**"；并给 `sys_oper_log` 增加 `before_value`/`after_value`（或明确"变更类操作统一记录到独立的 `sys_change_log`"）。

### S-8 设备/网关管理无数据主体，"设备在线率"无法计算

**证据**：`1...md:106` 监测员职责含"**设备状态确认**"；`:227` 驾驶舱指标含"**设备在线率**"；`:155` 要求"支持**心跳保活**" **对** `3...md:360`：`mon_point.gateway_code varchar(32)` 只是一个**字符串字段**；`:365` `online_status` 靠"应用维护"

**问题**：没有 `mon_gateway` / `mon_device` 表——**网关不是实体，只是点位上的一个字符串**。后果：① 无法表达"网关级"的心跳与在线状态（一个网关下挂 100 个点位，网关掉线时 100 个点位同时离线，但系统只能逐个报）；② `FR-802` 的"设备在线率"没有分母（分母应是设备/网关数，不是点位数）；③ 网关协议、型号、通信参数、维护记录无处存放。

**改法**：增加 `mon_gateway`（`gateway_code`、名称、协议、IP/端口、所属隧道、在线状态、最近心跳时间、启用状态），`mon_point.gateway_code` 改为引用它；增加心跳历史或至少"最近心跳时间"字段。

### S-9 采集频率上限与需求冲突，且"加密监测"无实现字段

**证据**：
- `1...md:81-82`：沉降/收敛类采集频率 **"5min~1h"**（即 300~**3600**s）
- `3...md:362`：`collect_freq_sec` *"采集周期（秒，**30~1800** 可配）"* —— 上限 **1800s = 30min**，**1h 不可配**
- `1...md:356`：黄级响应动作要求"**加密监测（采集频率加倍）**"，但 `mon_point` 只有静态 `collect_freq_sec`，**无临时/加密频率字段**

**改法**：`collect_freq_sec` 范围改为 `30~3600`；增加"**临时频率覆盖**"机制（如 `temp_freq_sec` + `temp_freq_until` + `temp_freq_reason`），并在 `1.6.3` 与 `FR-301` 中说明加密监测由预警级别自动触发、降级后自动恢复。

### 关于 `data_sample` 单条字节的工程估算（供 P0-4 容量校核与 P2 复用）

`3...md:758` 用 `B≈100B`、`2...md:342` 用 `~120B`。按 InnoDB 实际开销估算：

```
id            bigint        8B
point_id      bigint        8B
ts            datetime      5B
value         decimal(16,4) 8B
quality       tinyint       1B
source        tinyint       1B
receive_time  datetime      5B
+ 行头(5B) + 变长/事务id/回滚指针(6B) ≈ 11B
≈ 47B 净行 → 聚簇索引实占 ≈ 48~64B（含页开销与填充因子）
+ 二级索引 idx_point_ts ≈ (8+5+6) = 19B/条，加页开销 ≈ 24B
合计 ≈ 72~88B/条
```

**结论**：若把 `idx_point_ts` 提升为聚簇键（见 P2-4），可从约 88B/条降至约 64B/条，**1 年原始数据体量下降约 27%**。建议在 `3.12` 中给出**该级别的可复算估算过程**，而不是直接给一个 `B` 值。

## 8. 勘误与核验说明（评审自身的可追溯性）

大厂评审要求结论可复核。本节记录本次评审中一项**被推翻的初判**与全部机械核验结果。

### 8.1 已推翻的初判：`data_sample_minute` 唯一键「违反分区约束」不成立

**初判**：`3.数据库设计说明书.md:422` 的 `uk_point_minute(point_id, ts_minute)` 不含分区键 `ts_minute`，建表必然报 `ERROR 1503`。

**核验方式**：对 `L422` 原文做字符级检查。

```
$s = '主键：`PRIMARY KEY(id, ts_minute)`；唯一键：`uk_point_minute(point_id, ts_minute)`；按月分区。'
$s.Contains('point_id, ts_minute')  ->  True
([regex]::Matches($s,'ts_minute')).Count  ->  2
```

**结论：初判错误。** `uk_point_minute` 的列清单是 `(point_id, ts_minute)`，**明确包含分区键 `ts_minute`**；`PRIMARY KEY(id, ts_minute)` 同样包含。按 MySQL 官方约束（*"分区表达式中使用的每一列，都必须是该表每一个唯一键的一部分"*），**该表定义合法，可以正常创建**。

**影响**：配套子审计报告《3.数据库设计说明书.审计报告.md》的 **P0-1 及其派生的 P1-1 部分结论不成立**，已在该文件头部加勘误说明。**该报告其余发现（尤其 DB-P0-a/b/c、容量精算、`DROP PARTITION` 边界、`is_deleted` 静默错行、DDL 校验 SQL）经复核成立**，仍应作为整改输入。

**教训（也是本报告的建议之一）**：这类"一执行就知道"的问题，**不应该靠纸面评审来判断**——它恰好证明了 §1 P0-3 的结论：**全量 DDL 必须在真实 MySQL 上实跑一遍**。
